# 简历要点

本文是《系统设计说明书》的附录，正式设计以 `docs/系统设计说明书.md` 为准。下面是便于简历摘录的短句，不是系统设计正文。

下面每条都能在仓库里指到包或文档。数字只引用 README 与 `doc/M17-02-压测报告.md`、`doc/M17-03-故障演练复盘.md`，并注明是文档里的那一次记录，不是线上容量承诺。项目是演出抢票与票务订单（数量型票档、模拟支付），不是完整商城。

- 用 Java 21 与 Spring Boot 3.5.6 做模块化单体，按 `identity` / `event` / `inventory` / `purchase` / `order` / `payment` 等领域分包；跨域只经抢票、支付、退款编排，业务包不跨域调 Mapper。Flyway `V1`–`V17`，表前缀 `ft_`（README 记 48 张表）。API 统一 `/api/v1` 与 `{code,message,data,requestId,traceId,timestamp}`。

- 库存防超卖放在 `InventoryMapper` 的条件更新：`reserve` 要求 `available >= quantity`，`confirm` / `release` 要求 `reserved >= quantity`，以受影响行数成败，不用 `@Version`。三态账本 `total = available + reserved + sold`，库表带守恒 CHECK。预占、确认、释放与流水、限购在同一本地事务，`request_id` 重复提交不二次扣减。

- 抢票受理返回 HTTP 202 与 `QUEUED`，与 `ft_outbox_event` 同一事务写入；`OutboxPublisher` 发到 RocketMQ `ft-purchase`，消费端用 Inbox `(consumer_name, event_id)` 和 `ft_purchase_request` 处理租约建单。`QUEUED` 不等于抢到。M17-02 那次本地对比（200 次受理、报告中的约 40 QPS、0 错误、200/200 建单）把受理速度和订单完成量分开统计。

- 模拟支付以 `ft_payment_attempt.attempt_request_id` 唯一幂等。`OrderMapper.paidById`（`markPaid`）与 `closeById` 都只更新仍为 `PENDING_PAYMENT` 的订单，支付另加未过期条件，避免同时变成 `PAID` 与 `CLOSED`。超时关单由 `ft-order-close` 延迟消息触发，`OrderTimeoutScheduler` 扫过期订单兜底，收口都在 `OrderCloseService`（释放预占、不重复释放）。

- 可观测用 Actuator + Micrometer Prometheus。本地 Prometheus 抓 `/actuator/prometheus`，Grafana 预置看板「FlashTicket 运营监控」。就绪探针同时查 MySQL `SELECT 1` 与 Redis `PING`，失败返回 503 `SERVICE_UNAVAILABLE`。M17-03 演练记录：停 broker/proxy 后 3 笔受理留在 Outbox `PENDING`，恢复后补发为 3 笔订单。

- 质量资产在仓库内：README 记载后端 19 个测试类、183 个用例；`e2e/tests/smoke.spec.ts` 覆盖注册到退款的 Playwright 冒烟；压测脚本为 `e2e/loadtest/checkout.jmx`。前端是 Vue 3 双应用（用户端 Naive UI、管理端 Element Plus），pnpm workspace，中间件用 Docker Compose。
