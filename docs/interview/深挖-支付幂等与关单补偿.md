# 深挖：支付幂等与关单补偿

本文是《系统设计说明书》的附录，正式设计以 `docs/系统设计说明书.md` 为准。机制正文见「4.3.5 支付幂等」和「4.3.6 关单补偿」。

代码：`payment.service.PaymentService`、`payment.mapper.PaymentAttemptMapper`、`order.mapper.OrderMapper`（`paidById` / `closeById`）、`order.service.OrderService.markPaid`、`order.service.OrderCloseService`、`order.service.OrderTimeoutScheduler`、`order.service.RocketMQOrderCloseDelaySender`、`order.api.OrderTimeoutDelayConsumer`。

支付是 `MOCK_WALLET`：同进程里模拟渠道成功，不调用外部支付网关。

## 机制

**一订单一支付单**  
`PaymentService.createOrGet` 按 `order_id` 查找。没有则插入 `ft_payment`（`CREATED`，金额抄订单 `payable_amount_cent`，过期时间抄订单 `expire_at`）。唯一键 `uk_payment_order`，并发插入撞键后重查。调用方不能在 body 里改金额。

**尝试幂等：`attempt_request_id`**  
`POST /api/v1/payments/{paymentId}/mock-pay` 的 body 只有 `attemptRequestId`（`MockPayRequest`，最长 64）。`createAttempt`：

- 已有相同 `attempt_request_id`（`uk_attempt_request`）→ 返回 null，`mockPay` 直接把当前支付单返回，不再走确认
- 否则插入 `PROCESSING` 尝试。`uk_attempt_no (payment_id, attempt_no)` 再挡一次并发
- 支付单已经是 `SUCCEEDED` 时，在创建尝试之前就返回

这解决的是「用户连点 / 网关超时重试」把同一次支付执行两遍，不是无限换新请求号刷支付。新的 `attemptRequestId` 仍会再试一次，直到订单不再是 `PENDING_PAYMENT`。

**和关单抢状态**  
确认核心在 `PaymentService.confirm`，与 mock 回调写在 `mockPay` 的同一个 `@Transactional` 里：

1. `orderService.markPaid` → `OrderMapper.paidById`

```text
UPDATE ft_order
   SET status='PAID', paid_at=…, paid_amount_cent=…, version=version+1
 WHERE id=? AND status='PENDING_PAYMENT' AND expire_at > ?
```

2. 行数为 1 才继续：`InventoryService.confirm`、核销券、`EntitlementService.issue`、支付单/尝试 `SUCCEEDED`、订单流水 `PAYMENT_CONFIRMED`、通知 Outbox
3. 行数为 0：抛 `PAYMENT_ORDER_CLOSED`（事务回滚，库存不会被确认）

关单 `OrderCloseService.doClose` 使用对称条件：

```text
UPDATE ft_order
   SET status='CLOSED', closed_at=…, close_reason=…
 WHERE id=? AND status='PENDING_PAYMENT'
```

`closeById` 返回 0 时重读：已是 `CLOSED` 则幂等返回；否则视为已被支付，抛 `ORDER_NOT_CANCELLABLE`，**不会** `release`。返回 1 才释放预占、返券、写流水、发关单通知。

两边都要求当前行仍是 `PENDING_PAYMENT`。支付多一个 `expire_at > now`：期限过了但扫描还没关单，也不能付成 `PAID`。InnoDB 对同一行的更新互斥，后提交的语句看不到 `PENDING_PAYMENT`，影响行数是 0。不会出现又支付又关闭。

**关单补偿（两条路径，一个收口）**  
建单成功后 `PurchaseRequestProcessor` 调 `RocketMQOrderCloseDelaySender`，向 `ft-order-close`（tag `ORDER_CLOSE`）发延迟消息，延迟默认等于支付期限 15 分钟。发送失败只记日志。

`OrderTimeoutDelayConsumer`（组 `ft-order-close-cg`）到期调用 `closeByTimeout`。关单自身幂等，消费结果固定 `SUCCESS`，不靠 MQ 重试来保证正确。

数据库兜底是 `OrderTimeoutScheduler`：默认约 30 秒扫 `status='PENDING_PAYMENT' AND expire_at <= now`，逐单 `closeByTimeout`。延迟消息只让关单更准时；扫描器才是 MQ 丢消息或进程当时没发出去时的补偿。

用户取消走 `POST /api/v1/orders/{orderId}/cancel`，同样进入 `doClose`（`close_reason=USER_CANCEL`）。

## 怎么演示

按 `docs/interview/DEMO-10min.md` 拿到 `PENDING_PAYMENT` 订单后：

```bash
# 创建支付单（无 body）
curl -sS -X POST -H "Authorization: Bearer $USER_TOKEN" \
  "http://localhost:8080/api/v1/orders/$ORDER_ID/payments"

# 同一 attempt 连打两次
ATTEMPT=$(python3 -c 'import uuid; print(uuid.uuid4())')
curl -sS -H "Authorization: Bearer $USER_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"attemptRequestId\":\"$ATTEMPT\"}" \
  "http://localhost:8080/api/v1/payments/$PAYMENT_ID/mock-pay"
curl -sS -H "Authorization: Bearer $USER_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"attemptRequestId\":\"$ATTEMPT\"}" \
  "http://localhost:8080/api/v1/payments/$PAYMENT_ID/mock-pay"
```

第一次 `SUCCEEDED` 并出票；第二次仍是成功响应，但 `GET /api/v1/admin/inventory/$TIER_ID` 的 `sold` 不会再加。权益列表张数等于购买数量，不会翻倍。

竞争用另一张未支付订单，不要等满 15 分钟：

```bash
# 终端 A：取消（关单赢）
curl -sS -X POST -H "Authorization: Bearer $USER_TOKEN" \
  "http://localhost:8080/api/v1/orders/$ORDER_ID/cancel"
# 终端 B：立刻 mock-pay → 业务码 PAYMENT_ORDER_CLOSED，库存应回到 available（RELEASE），sold 不增加
```

反过来先 mock-pay 再 cancel：取消得到 `ORDER_NOT_CANCELLABLE`，订单保持 `PAID`，预占不会被释放。

延迟关单不适合塞进 10 分钟主路径。讲的时候打开 `RocketMQOrderCloseDelaySender` 和 `OrderTimeoutScheduler`，说明前者失败时后者仍会关。

## 面试怎么讲

幂等键要说清粒度。订单号只能保证「这一单最终怎样」，挡不住同一次点击被提交两次。`attempt_request_id` 是客户端这次支付动作的键，库上唯一；重复请求在确认之前返回。换一个新的 attempt id 表示用户又发起一次，那时再靠订单状态条件更新拒绝。

支付和超时关单是同一行上的两个合法终态，不是先查状态再更新。`markPaid`（`paidById`）和 `closeById` 都带 `WHERE status='PENDING_PAYMENT'`。输的一方看受影响行数，不根据自己内存里的旧对象继续扣库存或出票。支付赢了走 confirm + 权益；关单赢了走 release。`confirm`/`release` 本身还要求预占仍是 `RESERVED`，所以就算编排层重入，账本也不会加减两次。

补偿不要讲成「只有消息队列」。延迟消息是准时路径，`OrderTimeoutScheduler` 扫过期未支付订单是补偿路径，两者调用同一个 `doClose`。消息丢了，扫描仍能关单；消息重复了，条件更新行数为 0，不会第二次释放库存。

最后补一句范围：这是模拟渠道在一个 MySQL 事务里做完的。真实支付要处理渠道回调乱序和「渠道已扣款、本地未提交」，本仓库没有外部渠道，不要把 `MOCK_WALLET` 说成已对接微信或支付宝。
