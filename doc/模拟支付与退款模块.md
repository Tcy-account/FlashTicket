FlashTicket 业务需求设计 06：模拟支付与退款模块
Payment & Refund Management · V1.0 · 交易闭环核心模块
本模块是 FlashTicket 票务交易链路的最后一个核心环节，负责让用户从“抢票成功、订单待支付”走到“支付完成”，并且支持退款申请、审核、退款处理和交易对账。
本轮继续只做业务需求、状态机和架构设计，不编写代码或数据库 DDL。
一、模块定位与设计目标
第一版采用内部模拟支付渠道，不接入真实支付宝、微信支付或银行账户，也不发生真实资金划转。
但我们会按照支付系统的工程设计方式实现：
- 支付订单与业务订单分离。
- 支付请求幂等。
- 模拟渠道异步通知。
- 支付成功与订单超时关闭互斥。
- 退款申请、审核和执行分离。
- 完整支付流水、退款流水和对账。
- 支持重复回调、超时、服务重启及异常补偿。
这里最值得深入研究的不是支付页面，而是交易状态一致性和并发安全。

3.1 支付渠道选择
建议 V1 只使用一个内部渠道：
MOCK_WALLET（虚拟模拟支付）
它并不是用户真正充值的钱包，也没有账户余额。用户点击“模拟支付”后，系统按测试业务规则生成支付成功、失败或处理中结果。
优点是没有外部平台限制，可以稳定模拟各种并发和故障场景。
第二阶段可增加 MOCK_ALIPAY、MOCK_WECHAT 两种不同模拟适配器，展示策略模式与渠道接口设计，但不是第一版必需功能。
3.2 支付金额规则
项目	规则
金额来源	服务端订单应付金额
支付币种	CNY
金额单位	整数分
用户提交金额	不作为可信金额
支付金额	必须与订单应付金额一致
一笔订单	同一时间只允许一个有效支付尝试
订单过期	不再接受新的支付确认
已支付订单	不允许再次生成有效扣款
用户端不得通过修改 HTTP 请求中的金额，把 999 元票价改成 1 元。
即使只是模拟支付，也要保留支付金额验证、订单归属检查和状态约束。

状态流转规则
原状态	触发事件	目标状态
不存在	创建支付单	CREATED
CREATED	开始模拟执行	PROCESSING
CREATED / PROCESSING	支付确认成功	SUCCEEDED
CREATED / PROCESSING	确认失败	FAILED
CREATED / PROCESSING	订单关闭或支付过期	CLOSED

FAILED	重复失败结果	幂等返回失败

模拟渠道的失败结果必须是确定性失败，而不是把 HTTP 超时当作失败。对于暂时无法确认执行结果的情况，保持 PROCESSING 并通过恢复任务查询。
第一版允许失败后重新发起新的支付尝试，但旧尝试必须已经进入确定终态，新尝试要生成独立支付单，不能复用已经失败的支付流水。
五、最重要的设计：支付成功与超时关单竞争
我们此前已经确定订单状态：
PENDING_PAYMENT → PAID / CLOSED
支付确认与关单竞争必须有一个数据库认可的唯一胜出者。
推荐事务设计
订单 PENDING_PAYMENT


支付事务
获取订单状态转换权
更新支付单、订单、库存


关单事务
获取订单状态转换权
关闭支付单、订单、释放库存




一个合法终态
PAID 或 CLOSED，不会同时成立


推荐采用：
- 事务开始后按照固定顺序取得相关订单、支付单锁。
- 校验数据库当前订单状态和支付期限。
- 在同一个事务中改变支付单、订单、库存预占和库存流水。
- 同事务写入支付事件 Outbox。
- 事务提交后再异步通知用户。
Spring 本地声明式事务适合协调同一数据源中的这些数据库操作，而不能自动将独立 MQ Broker 或外部支付平台纳入同一事务。

六、退款业务需求
退款不是删除支付记录，也不是把订单状态直接改回待支付。
退款是一笔新的逆向交易，必须关联原支付、原订单和退款原因。
6.1 第一版退款规则
项目	推荐规则
退款申请人	已支付订单所属用户
退款条件	活动允许退款，且尚未达到退款截止时间
退款金额	第一版全额退款
部分退款	P2 扩展
同时进行的退款	同一订单最多一个有效退款申请
财务审核	FINANCE 或 SUPER_ADMIN
自己审核自己	禁止
模拟退款执行	内部模拟渠道
退款成功	保留原支付记录，新增退款流水
退款失败	支持重试或人工处理
退款回补库存	默认不重新上架
最后一条需要特别说明。
即使用户退款成功，也不代表这张票立即重新销售。演出可能临近、已停售或已经取消。
为了保持账本简单，第一版采用：
退款成功只撤销票务权益，不自动增加 available；库存中记录退款核销数量，后续再决定是否可重新发售。
我们之前的三态库存公式为：
\[
total=available+reserved+sold
\]

这里需要区分 sold 的含义：在 V1 中它是已确认售出的库存席位计数，退款后默认仍占用这个售出容量，避免在没有重售策略时直接释放。财务上的净销量由支付与退款流水另行统计。
如果 P1 实现退款后重新上架，再通过独立的 REFUND_RESTOCK 库存操作减少已售占用、增加可售数量，并写入库存流水。不能使用未支付预占释放的操作代替。
6.2 退款申请原因
第一版支持：
- 个人原因申请退款。
- 演出延期。
- 演出取消。
- 其他原因（填写说明）。
普通用户个人原因退款需要按照演出退票规则判断。平台取消活动时，则可以由系统发起批量退款，不要求用户逐笔申请。
退款政策在订单创建时也要保存相应版本或快照，防止运营人员事后修改规则影响已经成交的订单。

不应在审核通过时就告诉用户“退款成功”。

建议分成六张核心表。

- ft_order、ft_order_item
- ft_reservation、ft_inventory_ledger
- ft_outbox_event、ft_message_inbox
支付与退款流水的重要约束
- 支付单不能对应多个最终成功支付。
- 退款业务号不能因重复请求而重复生成。
- 一笔原支付累计成功退款金额不得大于原支付确认金额。
- 第一期全额退款，一笔成功支付最多发生一次最终全额退款。
- 历史支付单、回调记录和退款流水不能通过业务接口物理删除。
- 数据库使用唯一约束和状态条件更新兜底，Redis 锁只作为辅助。
这里不建议引入真实资金账户、复式记账总账或充值余额系统，因为我们的项目是票务平台，不是银行核心系统。

十、RocketMQ 消息设计
沿用已经确认的 RocketMQ 5.x、Outbox 和消费端 Inbox 幂等方案。
消息事件	Topic	主要用途
PAYMENT_PROCESS_REQUESTED	ft-payment-event	请求内部模拟渠道执行
PAYMENT_SUCCEEDED	ft-payment-event	非核心支付后续通知与统计
PAYMENT_FAILED	ft-payment-event	记录支付失败及后续通知
REFUND_APPROVED	ft-payment-event	触发模拟退款执行
REFUND_SUCCEEDED	ft-payment-event	退款完成后的通知与统计
REFUND_FAILED	ft-payment-event	失败处理与告警
这些消息采用 Normal 类型即可，暂时不依赖 FIFO 消息来保证支付或退款状态正确性。
核心支付确认事务不应依赖消费者接收 PAYMENT_SUCCEEDED 后才去凑齐最终数据库账本。 对于内部模拟渠道，应在数据库本地事务中完成支付最终状态、订单状态、库存状态和业务事件持久化，然后再通过 RocketMQ 通知下游。
RocketMQ 用于异步执行、削峰、通知和补偿，不作为唯一的交易事实来源。
十一、异常恢复与对账
故障场景	风险	处理原则
用户连续点击支付	多个支付请求	支付业务幂等，同一有效支付单
HTTP 响应丢失	用户不知道是否支付成功	查询已有支付单与订单状态
模拟支付回调重复	重复确认订单	回调去重与状态机幂等

票档库存异常回补	可售票数错误	不自动重上架，按独立库存调整流程
对账内容
建议从三个角度验证：
订单与支付对账： PAID 订单应存在对应的成功支付记录，且支付金额与订单确认金额一致。
支付与退款对账： 退款成功金额不能超过原支付金额，退款业务与执行尝试应可追溯。
交易与库存对账： 已支付和已退款订单的库存占用应符合当前“退款不自动重上架”的票务规则。
对账失败时不能直接覆盖金额或修改支付状态，应生成异常记录并明确补偿或人工处理路径。

十五、模拟支付与退款模块 V1.0 定稿
FlashTicket 支付与退款业务规则


支付模式： 内部 MOCK_WALLET 模拟渠道，不接入真实资金。
支付单： 与业务订单分离，支持创建、处理、成功、失败、关闭。
支付期限： 与订单 15 分钟有效期一致。
原子确认： 模拟支付结果、订单 PAID、库存 CONFIRMED 在同一 MySQL 事务中完成。
幂等规则： 支付单、回调、退款单和执行尝试均有独立唯一业务标识。
退款模式： 已支付订单允许按票务规则申请全额退款，财务审核后执行模拟退款。
库存规则： 退款成功后默认不重新上架，后续如需重售，走独立库存回补流程。
可靠性机制： 本地事务 + Transactional Outbox + RocketMQ + Inbox 幂等 + 定期对账。
技术重点： 支付与超时关单竞争、重复回调、退款幂等、账目一致性、异常恢复。
