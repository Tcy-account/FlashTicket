FlashTicket 全项目开发计划 V1.0
项目定位：Java 21 高并发票务抢购平台，采用模块化单体架构，前后端分离开发。
这份计划作为 FlashTicket 后续开发的主路线图。今后可以直接按照阶段编号推进，例如“开始 M02-03”，我们就围绕该任务确定接口、数据库变更、Java 后端实现、AI 前端任务和验收标准。
一、项目最终要达到的目标
完成后，FlashTicket 应当具备三方面的成果：
1. 完整的票务业务系统：用户能够从注册登录开始，完成浏览演出、选择场次、抢票排队、下单、模拟支付、退款、使用优惠券和查看消息；管理员能够配置活动、审批、监控和对账。
2. 有技术深度的 Java 后端：真实实现 MySQL 高并发事务、Redis Lua、RocketMQ、Outbox/Inbox、库存一致性、订单状态机、幂等恢复和风控。
3. 可展示、可测试、可解释的工程项目：有完整前端、自动化测试、Docker Compose 部署、真实压测数据、架构文档和故障恢复演示。
二、技术栈保持不变
层次	技术方案
后端	Java 21、Spring Boot 3.5.x、Spring MVC
安全	Spring Security 6、JWT、Redis Refresh Token
数据访问	MyBatis-Plus + 手写核心 SQL
数据库	MySQL 8.4 LTS、Flyway、HikariCP
缓存及并发	Redis 7.4、Lettuce、Lua、Redisson（按需）、Caffeine
消息系统	RocketMQ 5.x、Outbox/Inbox
用户端	Vue 3、TypeScript、Vite、Naive UI、Tailwind CSS
管理端	Vue 3、TypeScript、Vite、Element Plus、SCSS、ECharts
测试	JUnit 5、Mockito、Testcontainers、REST Assured、JMeter、Playwright
监控	Actuator、Micrometer、OpenTelemetry、Prometheus、Grafana
工程部署	Maven、pnpm workspace、Docker Compose、Nginx、GitHub Actions
架构坚持单 Spring Boot 应用、一个 MySQL 业务数据库、按业务域组织模块。不引入微服务、不接真实资金支付、不引入 AI Agent。

四、第一里程碑：账户基础（M00–M03）
这一部分就是你接下来应该开始的开发工作。
M00：项目工程初始化
后端任务
- 初始化 Java 21 Spring Boot 单 Maven 工程。
- 创建基础模块包结构。
- 配置 MySQL、Redis、本地环境变量。
- 配置 MyBatis-Plus、Validation、全局异常和统一 API 响应。
- 配置 Spring Security 基础结构。
- 接入 Flyway，但只创建当前功能需要的数据库对象。
- 建立健康检查与基础集成测试。
AI 前端任务
- 初始化 ticket-web、admin-web。
- 实现全局视觉 Token、布局和响应式设计。
- 配置 Axios、Pinia、Vue Router。
- 开发登录注册视觉页面和开发环境 API Lab。
- 实现前端代理和真实服务连接检测。
验收： 能在浏览器发出真实后端请求，并正确显示成功、失败和服务不可用状态。
M01：用户注册与邮箱验证

M01-03	邮箱验证码生成、发送与校验	发送按钮与倒计时

M03：后台账号与 RBAC
后端实现后台管理员登录入口、角色权限管理、用户列表、角色分配、账号禁用和敏感操作审计。明确 USER、OPERATOR、FINANCE、ADMIN、SUPER_ADMIN 的权限边界。
AI 前端实现后台登录页、管理端布局、用户管理表格、角色权限管理页面和操作弹窗。
验收：普通用户无法访问后台敏感接口；不同后台角色的功能与数据权限得到正确执行。

五、第二里程碑：演出上架（M04–M06）
M04：演出分类与场馆管理
后端实现演出分类管理、场馆创建编辑、场馆状态、城市筛选和容量校验。
AI 前端同步交付后台分类/场馆管理页面，以及用户端分类筛选入口。
验收： 管理员新建场馆后，用户端可以读取真实场馆或分类数据。
M05：演出活动和场次
后端实现：
- 活动草稿、编辑、列表与详情。
- 创建场次、设置演出开始和结束时间。
- 场馆时间冲突校验。
- 场次延期、取消的合法状态转换。
- 活动与场次的并发版本控制。
AI 前端负责活动编辑表单、活动列表、场次配置及用户端演出卡片、详情页面。
验收： 管理员创建活动和场次，用户端能查看；同一场馆发生时间冲突时，系统明确拒绝非法排期。
M06：票档、售票计划与审核发布
后端实现票档价格、数量、限购配置，售票窗口、运营暂停、审核快照及正式发布。
这里落实跨域审查中的活动配置指纹与冻结规则。
AI 前端实现票档配置表格、审核工作台、发布确认、场次及票档展示、开售倒计时。
验收： 未发布活动不能正常销售；审核通过的配置没有被篡改；用户端准确展示未开售、开售中、暂停等状态。

六、第三里程碑：完整交易闭环（M07–M11）
这一阶段是 FlashTicket 最重要的后端开发阶段。
M07：MySQL 库存总账与用户限购
后端任务：
- 库存初始化。
- total = available + reserved + sold 守恒。
- MySQL 原子条件扣减。
- 正式预占、确认、释放。
- 不可变库存流水。
- 用户票档限购占用。
- 并发测试和重复操作幂等。
前端 AI 实现后台库存查看、初始化反馈、库存操作展示，以及演出详情中的库存状态。
验收： 在真实 MySQL 中并发抢有限数量票，不出现超卖、负库存或重复释放。
M08：同步抢票与订单创建
这一阶段暂时不使用 RocketMQ。
实现真实的同步抢票事务：
请求校验 → 限购占用 → 库存预占 → 创建订单 → 返回订单结果
涉及 PurchaseCheckoutService、ft_purchase_request、ft_reservation、ft_order 和 ft_order_item。
AI 前端实现选择场次和票档、购买数量、抢票按钮、抢票反馈和我的订单页面。
验收： 用户在浏览器点击“立即抢票”，能够创建一笔真实待支付订单；库存与限购账目同时变化。
M09：取消订单和支付超时
后端实现订单状态机、用户取消、15 分钟支付期限、数据库超时扫描、库存释放、限购恢复和操作流水。
此时 RocketMQ 尚未接入，使用 Spring Scheduling 扫描作为基线实现。
AI 前端提供待支付倒计时、取消订单、订单详情和状态刷新。
验收： 用户取消订单或订单超时后，库存正确释放；重复点击或重复调度不会重复释放。
M10：模拟支付与票务权益
后端实现支付业务单、支付尝试、模拟渠道、支付结果确认、订单和支付的事务互斥，以及 ft_ticket_entitlement 票务权益。
AI 前端实现模拟支付收银台、支付结果页面、我的门票和票务凭证页面。
验收： 付款成功后订单成为 PAID、库存转为 sold，并为购买数量生成对应的有效门票权益。
M11：全额退款与权益撤销
后端实现退款申请、财务审核、模拟退款执行、结果幂等、退款记录与权益撤销。
AI 前端实现用户退款申请页面、退款进度，以及管理端财务审核页面。
验收： 退款成功后，订单仍保留原支付事实，但票务权益不可继续使用；不重复退款、不自动返还库存与优惠券。
完成 M11 时，整个系统已经拥有能够演示的同步交易完整闭环。此后再开始异步与高并发优化。
七、第四里程碑：异步化与高并发增强（M12–M15）
M12：RocketMQ 异步抢票与可靠消息
将已有同步抢票逐步升级成：
创建请求 → MySQL Outbox → RocketMQ → 消费者建单 → 持久化处理结果
开发内容包括 Outbox Publisher、Inbox 消费幂等、PushConsumer、执行租约、请求恢复、RocketMQ Delay 关单检查与数据库兜底。
AI 前端开发排队页、抢票状态页、进度实时刷新与失败原因展示。
关键约束： “排队中”不能显示为“抢票成功”，也不能展示虚构的精确排名或等待时间。
验收：消息重复、消费者重启、MQ 暂时不可用时，不重复创建订单，已受理的合法请求能够得到确定结果或进入可恢复状态。
M13：优惠券营销
后端实现营销活动、优惠券模板、额度账本、用户限领、领券请求、发券流水、用户券状态、订单锁券、支付核销与关单解锁。
AI 前端交付用户优惠券中心、领券页面、下单选券、后台营销活动与模板管理。
开发顺序应先做 MySQL 直接发券正确性，再按需要升级为 RocketMQ 异步领券。
验收： 不能超发、超领或重复核销，订单优惠金额不可被客户端修改。
M14：系统通知与 SSE
后端实现个人通知、接收人记录、业务通知去重、未读/已读状态、通知消费者与 SSE。
AI 前端开发消息中心、通知图标、未读数量、通知详情和业务跳转。
P1 的批量公告、固定受众快照在个人通知完成后再做。
验收： 支付或退款成功后可生成通知；用户离线后仍能查询；重复消费不产生重复消息。
M15：风控及 Redis Lua 优化
这个阶段拆成三个连续子任务：
子任务	内容	验收重点
M15-A	用户/IP/票档/接口多维限流	Redis Lua 原子限流
M15-B	风控规则、临时限制及后台操作	限制生效、解除、过期
M15-C	Redis 高速库存准入与恢复	性能提升同时不破坏 MySQL 正确性
必须保留三种可以独立比较的运行模式：
1. MySQL 同步抢票。
2. RocketMQ 异步抢票 + MySQL 原子库存。
3. RocketMQ 异步抢票 + Redis Lua 高速准入 + MySQL 最终账本。
验收： 经过 Redis 故障、过期资格、请求重试与重建代次测试，不能产生重复资格或突破真实库存。

八、第五里程碑：统计、对账与工程交付（M16–M17）
M16：运营统计、对账及补偿
后端完成运营日统计、演出销售统计、库存与预占对账、订单支付对账、退款对账、优惠券对账、Outbox 积压检查和补偿任务。
AI 前端完成 ECharts 运营工作台、对账任务、异常工单和补偿审批页面。
验收：通过受控故障测试制造可识别的不一致状态，对账能定位异常，安全补偿能恢复合法状态，而不是盲目篡改库存或资金数据。
M17：综合质量、压测与部署
这一阶段分为五个交付包：
编号	交付包	主要内容
M17-01	自动化测试	JUnit、Testcontainers、REST Assured、前端交互测试
M17-02	压测	JMeter 抢票、订单、支付、Redis 方案对比
M17-03	故障注入	MySQL 死锁、Redis 重启、MQ 故障、应用崩溃
M17-04	部署与监控	Docker Compose、Nginx、健康检查、Prometheus、Grafana
M17-05	项目文档	README、架构图、ER 图、API、压测报告、故障复盘
压测报告必须真实记录 QPS、P95/P99、请求失败率、最终订单完成吞吐、MQ 积压及数据库资源消耗。不能把接口返回 HTTP 202 的速度冒充真实抢票成功吞吐。

九、全项目的执行规则
为了保证这个计划真正能一直执行下去，我建议定下六条项目规则。
规则一：始终保证浏览器可验证。 每项功能都同时安排 Java 后端和 AI 前端任务。即使前端尚未制作正式产品页面，也应先通过开发专用 API Lab 真实调用接口。
规则二：一个阶段完成后才能进入依赖它的下一阶段。 不是要求所有代码零缺陷，而是核心成功路径、失败路径、权限控制和关键测试必须通过。
规则三：Flyway 跟随业务开发。 当前计划只确定功能顺序，不指定迁移版本号和固定表批次。每个任务开始时再确认需要新建或修改的表、索引和约束。
规则四：先正确，再优化。 库存、支付、退款先用 MySQL 事务保证合法状态，随后引入 MQ 和 Redis；不为了性能牺牲交易正确性。
规则五：接口契约由后端主导。 你实现 Java 后端，AI 负责 Vue 页面及 API 调用，任何接口字段变化都同步调整前端类型、错误反馈和测试。
规则六：每个阶段都有明确交付记录。 至少保存功能清单、数据库变化、API 列表、自动化测试结果、浏览器验收结论及未解决问题。
十、开发任务的统一模板
以后每次开始一个任务，建议按照以下结构开展：
任务编号：Mxx-xx
1. 业务目标：用户或管理员完成什么操作。
2. 模块依赖：涉及哪些已有领域服务，不允许出现什么循环依赖。
3. 数据库设计：本任务需要哪些表、字段、约束和索引。
4. API 契约：路径、请求、响应、权限与错误码。
5. Java 后端任务：Controller、Service、Mapper、事务及安全控制。
6. AI 前端任务：页面、交互、真实 API 接入和异常状态。
7. 自动化测试：正确性、幂等、权限、并发及故障场景。
8. 浏览器验收：具体点击什么、应当看到什么结果。
9. 完成标准：明确达到什么条件后进入下一任务。
