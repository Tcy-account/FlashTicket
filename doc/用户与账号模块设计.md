三、注册与登录业务
3.1 普通用户注册
第一版建议采用 用户名 + 密码 + 邮箱验证。
暂时不接入手机短信服务，原因是短信涉及服务商、成本、风控和外部依赖，不是当前 Java 实习项目的核心重点。
1. 用户填写用户名、邮箱、密码和确认密码。
2. 系统校验用户名格式、邮箱格式、密码强度和是否重复。
3. 向邮箱发送一次性验证码，验证码有有效期和发送频率限制。
4. 用户提交验证码，服务端完成原子核销。
5. 创建账号，默认赋予 USER 角色，状态设置为正常。
6. 注册完成后跳转登录页面，不自动签发登录令牌。

注册规则：
项目	规则
用户名	4–32 个字符，英文字母、数字、下划线
用户名唯一性	不区分英文大小写
邮箱	必须验证、全局唯一
密码	12–64 个字符，支持密码管理器生成的复杂密码
密码强度	拒绝常见或已泄露密码，不强制必须包含所有字符类型
验证码	6 位数字，有效期 5 分钟
验证码错误	同一验证码最多尝试 5 次
邮件发送频率	同一邮箱 60 秒内最多发送一次
验证码用途	注册、找回密码、换绑邮箱互相隔离
注册默认角色	USER
注册成功行为	返回成功，用户主动登录
OWASP 对认证安全的建议包括登录限速、避免弱密码、敏感操作重新认证，以及使用合理的密码强度规则。

3.2 登录方式
第一版：
- 用户名 + 密码。
- 已验证邮箱 + 密码。
用户端登录地址与管理端登录地址分开，但共用认证服务和用户身份主体。
场景	用户端	管理端
普通用户登录	允许	禁止
运营人员登录	有 USER 角色才允许使用个人购票功能	允许
财务人员登录	同上	允许
系统管理员登录	同上	允许
超级管理员登录	按实际分配的前台角色判断	允许
后台登录必须校验账号具有有效后台角色，不能只凭 JWT 签发成功就进入后台。
3.3 登录失败与账号保护
建议设置两层保护机制，避免用户被攻击者无限尝试密码。
项目	建议策略
连续密码错误	5 次触发临时登录保护
临时锁定	10 分钟
错误计数窗口	15 分钟
IP 限流	独立 Redis 限流
账号维度限流	独立计数，防止多 IP 绕过
登录成功	清除当前密码错误计数
未知用户名	统一错误信息，不泄露账号是否存在
被锁定账号	不能再执行密码登录
账号锁定只影响新的身份认证，不改变账号永久状态。还应配合渐进式限流或验证挑战，避免恶意用户通过故意输错密码长期锁死其他人的账号。

令牌管理规则
项目	业务决定
Access Token	15 分钟
Refresh Token	7 天绝对有效期
Access 签名	RS256
Refresh 存储	Redis 保存令牌哈希及会话状态
Token 刷新	每次刷新轮换，旧令牌作废
会话唯一标识	sessionId
设备标识	一个登录设备对应独立会话
退出当前设备	撤销当前会话
退出全部设备	撤销该用户全部会话
多设备登录	普通用户最多 5 个有效会话，超出时要求选择下线设备
权限变更	相关后台会话立即撤销并重新登录
Access Token 尽量由前端保存在内存中；Refresh Token 放在 Secure + HttpOnly Cookie 中，并实施 SameSite、CSRF 防护和 Origin 校验。
刷新接口需要考虑并发刷新：同一个 Refresh Token 被浏览器多个请求同时使用时，不能轻易误判为攻击。建议前端单飞刷新，服务端进行原子轮换和短暂的并发容错，但不允许旧令牌被无限重复换新。
Spring Security 提供 JWT 认证的资源服务器能力，但本项目仍需自行实现 Refresh Token 会话与轮换规则。

六、密码与账号安全
6.1 密码存储
推荐使用 Spring Security PasswordEncoder，第一版采用 BCrypt。
- 不保存明文密码。
- 不通过日志输出密码。
- 不允许管理员查看用户密码。
- 修改密码时验证当前密码。
- 找回密码通过一次性验证码重置。
- 重置成功后撤销已有会话。
Spring Security 官方推荐使用专门的单向密码编码器，而不是直接使用普通 SHA-256 等快速哈希保存用户密码。

七、账号状态设计
这里必须区分 账号状态、登录保护状态、注销流程状态，否则后续逻辑会非常混乱。
7.1 账号主状态
状态	含义	是否允许登录
ACTIVE	正常	是
DISABLED	管理员停用	否
DELETION_PENDING	注销处理中	否
DELETED	已完成删除或不可逆匿名化	否
LOCKED 不建议放入主状态枚举，因为登录失败触发的临时锁定和管理员主动禁用不是一个概念。
7.2 状态流转
主要状态流转示意。注销中的账号如在规定期限内撤销申请，可经过安全校验恢复正常；最终注销后不可恢复原账号。
7.3 注销账号如何处理已有订单？
这是票务项目必须考虑的问题。
用户可能存在未支付、已支付、等待退款或尚未使用的门票。
我建议：
- 有未完成订单、退款或尚未履行的票务权益时，阻止最终注销，并明确提示需要处理的事项。
- 注销申请受理后立即撤销所有登录会话，进入限制访问状态。
- 允许在规定撤销期内通过身份验证撤销申请。
- 对需要依法或按争议处理要求保留的交易凭证进行受限保留，其他个人信息按隐私规则清理或匿名化。
- 不能因为账号注销就直接删除订单和资金流水，从而破坏对账。
第一版可以先实现账号停用与注销申请，完整的数据匿名化处理放到 P1。
八、后台账号与 RBAC 管理
我们此前已经确认五种正式角色：
USER、OPERATOR、FINANCE、ADMIN、SUPER_ADMIN。
建议统一使用一个用户主体和 RBAC 权限体系。
后台功能
功能	操作人员	规则
创建员工账号	ADMIN / SUPER_ADMIN	账号通过邀请设置密码
查询员工列表	ADMIN / SUPER_ADMIN	支持状态、角色、用户名筛选
修改员工资料	ADMIN / SUPER_ADMIN	不修改历史审计身份
分配业务角色	ADMIN / SUPER_ADMIN	不允许越权授予角色
禁用员工账号	ADMIN / SUPER_ADMIN	立即阻止敏感 API
强制下线	ADMIN / SUPER_ADMIN	撤销指定用户会话
配置角色权限	SUPER_ADMIN	审计记录
查看安全审计	授权管理员	仅可查看授权范围
必须遵守这些规则：
1. 普通注册用户不能通过 API 自行授予后台角色。
2. ADMIN 无权授予 SUPER_ADMIN，也不能提升自己的管理权限。
3. 系统至少保留一个有效超级管理员，不能禁用或删除最后一个。
4. 后台权限变化应使相关登录会话失效。
5. 角色权限不等于数据权限。运营人员查询订单还需要对应的数据范围检查。
建议超级管理员由数据库初始化迁移后的独立安全引导流程创建，不在代码或公开种子数据中硬编码生产密码。

建议同时区分登录审计与后台敏感操作审计。

十四、开发优先顺序
建议用户模块分三期，不要因为完善账号管理而延误高并发抢票主线。
阶段	功能范围	阶段验收
第一阶段 P0-A	统一账号、密码登录、JWT、Refresh Token、基础资料	能登录并访问个人 API
第二阶段 P0-B	注册邮箱验证、修改重置密码、RBAC、后台员工管理、账号禁用	权限与账号安全闭环
第三阶段 P1	多设备管理、审计日志、MFA、注销流程完善	安全功能与管理功能完整
实施时应优先完成 P0-A 和最基本的后台身份授权，然后进入活动与票档模块。P0-B 的非阻塞功能可在交易主链路完成前补齐。
十五、本轮需求定稿
FlashTicket · 用户与账号模块 V1.0

身份体系
统一用户账号，用户端与管理端分离入口，采用五种角色及 RBAC 权限模型。
认证方式
用户名 / 已验证邮箱 + 密码，JWT Access Token 15 分钟，Redis Refresh Token 最多 7 天。
账号安全
BCrypt 密码哈希、邮箱验证、登录限制、敏感操作重新认证、会话撤销和账号禁用。
账号管理
普通用户管理个人资料，管理员管理后台员工和角色权限，超级管理员管理全局授权。
实现边界
暂不接入短信、微信登录、实名认证、第三方支付和完整复杂身份治理。

这套账号模块足以支撑 FlashTicket 后续的演出管理、抢票、订单、模拟支付和财务管理，也有较强的 Spring Security、Redis、MySQL、RBAC 面试价值。
