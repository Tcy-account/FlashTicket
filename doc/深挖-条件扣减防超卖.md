# 深挖：条件扣减防超卖

代码：`inventory.mapper.InventoryMapper`、`inventory.service.InventoryService`。表：`ft_inventory`、`ft_reservation`、`ft_inventory_ledger`、`ft_purchase_limit`（`V7__inventory_reservation_ledger_limit.sql`）。

## 机制

一票档一行总账，主键就是 `tier_id`。守恒式：

```text
total = available + reserved + sold
```

数据库有 `chk_inv_conservation` 以及各列非负 CHECK。应用层不先 `SELECT` 再在 Java 里减，而是一条条件 `UPDATE`，用受影响行数判断成败。`version` 只在 `SET` 里 `+ 1`，**不**放进 `WHERE`，也没有 MyBatis-Plus `@Version`。并发安全来自「`available >= q` / `reserved >= q` + InnoDB 行锁」，不是乐观锁冲突重试。

`InventoryMapper` 三条语句：

| 方法 | 效果 | 条件 |
|---|---|---|
| `reserve` | available -= q，reserved += q | `tier_id` 且 `available >= #{quantity}` |
| `confirm` | reserved -= q，sold += q | `reserved >= #{quantity}` |
| `release` | reserved -= q，available += q | `reserved >= #{quantity}` |

返回 1 才继续写预占/流水；返回 0 表示可售或预占不足。`reserve` 返回 0 抛 `INVENTORY_SOLD_OUT`。

`InventoryService.reserve` 在同一事务里做四件事：

1. 按 `request_id` 查 `ft_reservation`，已有则直接返回（客户端重试不二次扣减）
2. `inventoryMapper.reserve`
3. 限购：`PurchaseLimitMapper.selectForUpdate`，`reserved + sold + q` 不得超过票档 `per_user_limit`，再 `addReserved`
4. 插入 `RESERVED` 预占（`request_id` 唯一兜底）并写流水 `RESERVE`

`confirm` / `release` 先改预占行：`ReservationMapper` 仅当 `status='RESERVED'` 才转到 `CONFIRMED` 或 `RELEASED`。行数是 0 就重读；已经是目标终态则幂等返回。已确认的预占不能再当普通释放（退款回补是另一条业务）。库存行与限购行在预占状态转成功之后才动，流水操作名是 `CONFIRM` 或 `RELEASE`。

谁调用：建单事务 `PurchaseOrderBuilder.build` 调 `reserve`；`PaymentService.confirm` 调 `confirm`；`OrderCloseService.doClose` 调 `release`。库存包不创建订单、不改支付单。

Redis 准入（`InventoryAdmissionService`，默认关闭）只做入口预检。快照售罄可以提前拒绝，最终是否超卖仍由上面的 `UPDATE` 决定。

## 怎么演示

按 `doc/DEMO-10min.md` 走到抢票 `SUCCEEDED`、尚未 mock-pay：

```bash
curl -sS -H "Authorization: Bearer $ADMIN_TOKEN" \
  "http://localhost:8080/api/v1/admin/inventory/$TIER_ID"
```

相对初始库存：`available` 少 1，`reserved` 为 1，`sold` 仍为 0。流水 `GET …/ledger` 有一条 `RESERVE`。

同一 `requestId` 再 `POST /api/v1/purchases`，账本数字不变。

mock-pay 成功后再查：`reserved` 减少、`sold` 增加，流水多一条 `CONFIRM`，`total` 不变。

若要讲「卖光」：把 `initialQuantity` 设得很小，或连续用不同用户买完。多出来的请求在消费端失败，抢票状态 `FAILED`，原因码来自 `INVENTORY_SOLD_OUT`（写入 `fail_reason`，最长 32）。受理接口本身仍可能先 202，因为受理不扣 MySQL 库存。

对账口：`GET /api/v1/admin/inventory/{tierId}/reservations`。

## 面试怎么讲

先否定「读出来再减」：两个事务都能读到 available=1，然后都写入 0，超卖。这里把判断留在存储引擎里：`UPDATE … WHERE available >= q`，行锁让后到的更新看到已提交的值，条件失败则影响行数为 0。

三态比「一个 stock 字段」好讲清业务：下单只是预占，支付才算卖出，超时必须把预占还回可售，而且不能把已经卖掉的票加回去。所以 confirm/release 的条件是 `reserved >= q`，预占行再用 `WHERE status='RESERVED'` 保证一次只进入一个终态。

幂等分三层，不要混成一句「加了唯一索引」：请求号防重复预占，条件更新防重复改账，流水只是审计不是锁。

Redis 要放在最后：它降低打到 MySQL 的无效请求，账本仍在 `ft_inventory`。模式对比的数字以 `doc/M17-02-压测报告.md` 那次本地 200 请求为准，不要说成生产 QPS。
