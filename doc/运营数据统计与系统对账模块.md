FlashTicket 业务需求设计 10：运营数据统计与系统对账模块
推荐方案 V1.0
Analytics & Reconciliation · 业务需求设计

这是 FlashTicket 业务规划中的第十个模块，也是把前面九个模块连接成完整运营闭环的最后一个核心模块。
我们要实现两套相互关联、但职责不同的系统：
- 运营数据统计（Analytics）：帮助运营人员了解演出销量、订单转化、优惠券效果以及抢票系统的运行状况。
- 系统对账与补偿（Reconciliation）：检查订单、库存、支付、退款、优惠券和异步消息之间是否一致，并安全处理异常。
最重要的架构原则是：
统计数据允许一定延迟，核心交易账目不允许为了统计效率而牺牲正确性；对账发现差异也不意味着可以直接修改账本。
本轮仍然只设计业务需求、系统架构、数据实体、接口、异常处理和验收标准，不写 Java 代码或数据库 DDL。

二、运营统计指标定义
设计运营看板前，必须先统一指标口径。
否则可能发生前台显示卖出 100 张票，后台订单统计 120 张，财务统计收入却对应 95 张的情况。
2.1 订单与销售指标
指标	计算口径
抢票受理数	指定时间段成功持久化的抢票请求数
抢票成功数	最终成功创建待支付订单的请求数
订单创建数	指定时间段创建的订单数
支付订单数	指定时间段确认支付成功的订单数
销售票数	已支付订单对应的票数，退款另行统计
原价成交额	已支付订单优惠前金额合计
优惠金额	已支付订单使用的优惠金额合计
实收金额	模拟成功支付的金额合计
成功退款金额	已确认成功的模拟退款金额合计
净收入	实收金额减去成功退款金额
V1 的金额均为模拟交易金额，运营看板应明确标注“模拟数据”，不把它当作真实资金收入。
2.2 三种转化率不能混用
\[
抢票成功率=\frac{创建成功订单的抢票请求数}{已完成处理的有效抢票请求数}
\]

\[
订单支付率=\frac{已支付订单数}{已创建订单数}
\]

\[
退款率=\frac{已成功退款订单数}{已支付订单数}
\]

这些比率需要固定时间和人群口径。例如当日创建订单可能到次日才支付，因此按创建日期划分的订单支付率，应允许后续更新。
统计页面要显示指标的时间范围、口径以及最后更新时间。

三、统计系统的架构选型
这里不建议直接引入 ClickHouse、Flink、Kafka 或 Elasticsearch。
FlashTicket 当前是 Java 模块化单体，而且业务数据主要在 MySQL 中。我们可以使用现有技术完成完整的统计体系。
推荐：MySQL 汇总表 + RocketMQ 增量事件 + 定时校准

统计一致性策略
场景	推荐处理
新订单支付成功	产生持久化业务事件
统计消费者重复消费	按事件 ID 幂等处理
RocketMQ 短暂不可用	Outbox 恢复事件发送
统计服务停止	恢复消费，并按需重新校准
订单金额发生退款变化	产生独立退款事件，更新相应指标
增量统计出现误差	根据 MySQL 交易事实按固定时间窗口重算
历史统计重新计算	用批次和水位线管理，防止与实时增量重复计算
重点：统计表可以重建，原始交易账本不能因为统计重算而被覆盖。
MySQL InnoDB 的 MVCC 和事务一致性读可以支持汇总任务获得一致视图，但跨多批次、并发写入的统计仍需定义明确的数据截止水位线。

统计更新时间要求
建议初步设定：
- 运营概览：目标 5–30 秒延迟。
- 演出销量：目标 5–30 秒延迟。
- 小时趋势：每 5 分钟校准。
- 每日统计：次日生成日报，并允许迟到事件修订。
- 财务对账：按照确定的交易截止水位线运行，不要求毫秒级实时。
这些均是业务设计目标，不是当前系统已经验证的性能指标。
四、演出、抢票和营销分析
4.1 演出维度统计
指标	说明
活动销售金额	对应活动的已确认模拟支付金额
场次销售金额	某一场次的成交金额
票档销量	某一票档已确认售出的票数
库存占用率	(reserved + sold) / total
已支付售票率	sold / total，包含退款后未重新上架的容量
超时关单数量	未支付到期关闭的订单数
退款订单数量	成功退款的订单数
销售趋势	按小时、天观察销售变化
因为已经确定退款后门票默认不重新上架，所以 sold 代表已售占用容量，不等于扣除退款后的净有效票数。
这两项在运营看板中必须分别展示。
4.2 抢票性能统计
这个部分和业务销售指标不同。
指标	说明
请求受理 QPS	每秒被可靠受理的请求
排队等待耗时	从受理到实际开始处理
抢票处理耗时	从开始处理到终态确认
抢票成功率	有效已完成请求的成功比例
超时与恢复请求数	异常恢复情况
MQ 积压	待处理消息规模
数据库库存锁等待	热点库存竞争
限流拒绝数量	风控拦截量
这里建议运营业务统计数据存 MySQL，技术性能指标存 Prometheus。
不要把每秒 QPS、JVM GC、CPU 等时间序列监控数据都写入 MySQL 业务统计表。
Spring Boot Actuator 与 Micrometer 可以向 Prometheus 暴露应用指标，再由 Grafana 展示。

4.3 优惠券营销统计
指标	计算口径
发行额度	优惠券模板核定总量
已发券数	成功生成的用户优惠券
已使用券数	成功核销的优惠券

五、系统对账的总体原则
对账不是一个统一执行的 COUNT(*) 查询，而是根据业务关系核对不同账本。
我建议分成六个对账领域。
对账领域	检查内容	优先级
库存对账	总量、预占、已售、库存流水	P0
订单对账	抢票请求、订单、库存关联	P0
支付对账	支付单、订单状态、支付金额	P0
退款对账	退款单、执行结果、累计退款金额	P0
优惠券对账	发行额度、用户券、订单核销	P1
消息与任务对账	Outbox、恢复请求、超时任务	P0

三条核心约束
1. 对账操作必须有固定的检查范围和数据截止点。 否则边读边写产生的正常变化可能被误认为异常。
2. 重复执行同一对账任务不能制造新的业务流水。 对账任务和补偿操作分别维护幂等标识。
3. 不明原因的资金或库存差异默认不能自动修复。 必须先确认正确事实及影响范围。
六、库存对账设计
沿用之前确定的库存模型：
\[
total=available+reserved+sold
\]

但我们需要同时核验库存总账、预占记录与已支付订单之间的关系。
6.1 核验内容
检查项	正常规则	异常举例
总量守恒	total = available + reserved + sold	库存数量不平衡
非负库存	所有数量不小于 0	可售库存 -1
预占匹配	RESERVED 预占数量与账本 reserved 一致	账本预占 20，明细只有 19
已售占用	CONFIRMED 预占及合法后续调整与 sold 一致	支付订单对应库存未确认
唯一预占	同一 requestId 不重复占用	重复创建预占
流水记录	每次库存账目变化都有唯一流水	调整有结果、没有流水
Redis 准入预算	与数据库及在途预占相符	Redis 多发了资格

6.3 Redis 库存对账
由于之前已采用 Redis Lua 高速预占，不能直接要求：
Redis 库存 = MySQL available
更准确的设计是：
Redis 可发放资格 = MySQL 可售库存 − 尚未持久化且仍有效的 Redis 预占资格，前提是基于同一个已冻结或有可靠水位线的销售代次进行核算。
如果存在旧代次请求、无法确认的在途操作，必须先隔离并恢复，不能直接重建 Redis 数量后开放抢票。

七、订单、支付和退款对账
7.1 订单对账
订单状态	必须满足的条件
PENDING_PAYMENT	有有效库存预占，订单尚未过期或等待合法关单
PAID	有最终成功的支付记录及确认的库存占用
CLOSED	不存在仍有效的订单库存预占
REFUNDED 展示终态	存在合法成功退款，且订单票务权益按退款规则处理
其中 REFUNDED 可以采用已支付订单加退款成功派生的展示状态，不必强制再扩展订单数据库主状态。
7.2 支付对账
支付成功应至少满足：
- 订单为已支付状态。
- 存在唯一的有效成功支付结果。
- 成功支付金额等于订单应付金额。
- 支付币种一致。
- 支付与订单之间的关联正确。
- 对应库存已经确认已售。
- 支付结果和订单状态转换有审计记录。
一笔订单存在两条成功支付记录属于严重异常，不允许直接删除其中一条来“修复”。
7.3 退款对账
第一版只做全额模拟退款。
\[
累计成功退款金额\leq原支付成功金额
\]

还应检查：
- 一个退款业务 ID 最多有一次最终有效成功。
- 多次执行尝试不会产生多笔独立退款。
- 退款审核、执行和完成状态合法。
- 实际退款金额与退款单金额一致。
- 已退款票券默认不重新上架。
- 使用优惠券的订单按实际支付金额退款。
退款成功后的售出占用仍可以保留在库存 sold 里。 这符合此前确定的“退款不自动重新上架”规则，但需要在统计页面明确区分销售占用数量与净有效售票数量。
八、优惠券发行与使用对账
优惠券发行额度采用已经确定的模型：
\[
总发行额度=剩余额度+预留额度+已发行额度
\]

需要核验：
对账项目	检查内容
模板发行额度	发行总量没有超出核定额度
用户券明细	已发行数量与用户券记录一致
用户限领	每用户的成功领取量不超过限制
使用状态	一张用户券最多存在一个有效锁券订单
核销状态	USED 的券对应合法已支付订单
关单返券	CLOSED 订单不遗留无效 LOCKED 券
退款处理	V1 退款成功不重复返券
Redis 领券资格	与数据库发行账本及在途资格一致
运营人员发现异常时，不能直接修改模板发行数量。应形成带唯一操作号的额度调整、回收或补偿流水。
九、Outbox、Inbox 与异步任务恢复
这是本模块的技术重点之一。
我们之前已经决定使用 Transactional Outbox、Inbox 和 RocketMQ 至少一次消费。
本模块应提供统一异常监控与恢复入口。
9.1 需要监控的任务
任务	可能异常	恢复方式
Outbox 发布	Broker 不可用、发送超时	保留事件，延迟重发
Inbox 消费	消费者中断、重复投递	幂等判断、按业务状态恢复
抢票处理	处理租约超时	重新领取处理资格
Redis 预占	临时预占无法确认	检查请求，确认或释放
超时关单	Delay 消息延迟或漏处理	数据库到期扫描
模拟退款	执行结果不确定	查询退款尝试并恢复
异步发券	额度预占未落库	领取请求恢复与额度对账
批量通知	分发中途崩溃	依据进度恢复处理
RocketMQ 官方明确指出，消费重试是针对可恢复失败的兜底机制，不应该用它来处理所有正常业务分支。

9.2 自动补偿分级
我建议将补偿动作分为三级。

L1：可安全重试
例如 Outbox 未发送、幂等的通知创建任务失败。允许自动重试，并设置次数上限和退避时间。




L2：验证后补偿
例如预占超时、关单遗漏、优惠券异常锁定。必须核验当前订单、库存及原始操作状态，再执行幂等补偿。




L3：需要人工复核
例如支付金额不一致、重复成功支付、库存流水缺失且无法确定原因。禁止系统自动猜测正确金额或库存。



补偿任务状态
建议：
PENDING → RUNNING → SUCCEEDED / RETRY_WAIT / MANUAL_REVIEW
对于处理结果暂时无法确定的任务，使用 RECOVERING 或对应待决状态，不直接改成失败终态。
同一补偿动作必须有稳定的 operationId。消费者重复、调度任务重复或人工多次点击重试，都不能使同一笔库存重复释放、重复退款或重复发券。
十、对账任务与异常工单状态机
对账任务和对账异常需要分开管理。
10.1 对账任务
PENDING
等待执行


RUNNING
按批次检查，保存执行进度


SUCCEEDED
本次检查完成


FAILED
任务执行失败



任务检查成功不代表没有业务异常。SUCCEEDED 只表示扫描完整执行，发现的差异作为独立异常工单管理。
10.2 异常工单
建议采用：
OPEN → INVESTIGATING → RESOLVED → CLOSED
其中：
- OPEN：对账发现异常，等待处理。
- INVESTIGATING：管理员或自动补偿服务正在分析。
- RESOLVED：差异已安全修复或经确认不再存在。
- CLOSED：完成复核和归档。
对于误报使用 FALSE_POSITIVE 结果类型记录原因，而不是直接删除异常工单。
10.3 自动恢复不能无限循环
每个自动补偿任务建议记录：
字段	作用
attempt_count	已执行次数
max_attempts	最大自动尝试次数
next_retry_at	下次执行时间
last_error_code	最近错误码
lease_owner	当前处理者
lease_until	处理租约
operation_id	幂等操作标识
超过自动恢复次数，或遇到不能安全确定结果的错误，应进入人工复核。

关键唯一性规则
- 同一个聚合粒度和统计时间窗口只有一条有效汇总记录。
- 同一个统计消费者与事件 ID 只能应用一次有效增量。
- 同一范围、对账类型和执行批次不能重复领取执行权。
- 同一业务差异不能无限生成重复的未关闭异常工单。
- 每个补偿动作必须有唯一业务操作标识。
- 数据重算需要版本或水位线，防止旧批次覆盖新结果。

沿用之前确定的 Spring Scheduling + ThreadPoolTaskScheduler，不再引入 XXL-JOB。

全量历史对账	低峰期或手动	资源消耗较大
这是建议的开发配置，需要根据压测结果和任务积压情况调整。
即使后续部署多个同样的 Spring Boot 实例，任务也应通过 MySQL 状态条件更新及租约机制获取处理权，不能指望普通 @Scheduled 自动保证整个集群只运行一次。
数据库隔离
建议使用独立的对账和统计线程池及并发限制，但仍连接同一个业务 MySQL。
长时间统计查询要控制批次，避免压测时与抢票事务争夺过多连接和数据库资源。
不要把几百万条订单一次性加载进 JVM 内存。

十七、模块 V1.0 最终决策
FlashTicket 运营统计与系统对账方案


统计架构： MySQL 原始交易记录 + 汇总表 + Spring Scheduling；P1 增加 RocketMQ 增量统计和定时校准。
数据展示： Vue 3 + Element Plus + ECharts，业务金额均标注为模拟交易。
统计一致性： 允许准实时延迟，支持事件幂等、截止水位线和历史重算。
对账领域： 库存、订单、支付、退款、优惠券、异步消息和恢复任务。
异常管理： 差异检测、异常工单、分类处理、人工复核与审计。
自动补偿： 只执行能够确认正确性且具备幂等保障的操作；资金及库存疑难差异进入人工复核。
任务调度： Spring Scheduling + MySQL 租约 + 独立的有界执行资源。
监控体系： Micrometer + Prometheus + Grafana，重点观察 MQ 积压、对账延迟、补偿失败及数据库负载。
