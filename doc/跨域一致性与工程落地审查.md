UNIQUE(order_item_id, ticket_seq)
退款成功必须在本地事务中撤销全部权益。

- ft_order：交易是否支付成功。
- ft_refund：是否发生退款。
- ft_ticket_entitlement：当前是否拥有有效票务权益。

C02：支付与订单超时关闭边界
之前设计支付由模拟渠道返回结果，再尝试把订单改成 PAID。
但如果模拟渠道先返回成功，数据库事务尚未提交，此时关单又开始执行，就可能出现不确定的支付结果。
本次确定 V1 模拟渠道不独立产生真实资金侧的不可逆成功事实。
操作	最终规则
创建支付尝试	只创建 Attempt，不产生资金成功事实
模拟执行	可以模拟失败、延迟、超时
最终确认成功	必须取得订单合法转换资格
支付截止	按数据库统一时间基准执行
订单已关闭	不允许重新支付成功
模拟支付成功	订单、支付、库存、限购、优惠券、权益同事务确认
对于真实支付渠道，未来需要另外设计渠道结果与本地订单状态之间的补偿机制，不沿用这个简化假设。
特别修订： 在数据库锁定订单后，以同一权威时间基准判断是否过期。严格条件为 now < expire_at。不允许通过提前创建 Attempt 来无限延长支付时间。
C03：统一全系统锁顺序
此前建单、支付、关单各自给出了锁顺序建议，但并未完全统一。
这可能形成：
- 建单事务：先库存，再限购。
- 另一建单事务：先限购，再库存。
- 关单事务：先订单，再库存、再优惠券。
如果多个事务交错，就有形成死锁的风险。
建议制定一套所有交易路径共用的锁获取协议。
事务类型	需要遵守的原则
抢票建单	先锁定请求执行权，然后依固定顺序操作限购、库存、优惠券
支付确认	以订单作为状态转换入口，再访问已有支付、库存及权益相关数据
订单关闭	与支付确认使用完全一致的既有记录锁定顺序
优惠券领券	用户限领与模板发行额度遵循固定顺序
退款	先确定原订单，再处理退款单及权益
库存调整	必须与正常库存操作使用相同库存账本锁
工程规则： 锁顺序必须以实际 SQL 访问的记录顺序为准，不是仅在设计文档中列一个顺序。
此外，主键插入、唯一索引冲突、外键检查和 InnoDB 内部锁也会参与锁竞争。不能把固定锁顺序理解为完全消灭死锁，业务事务仍需具备有限重试。

C05：演出审核和发布版本不一致
第二批中存在：
- ft_event.version
- ft_event_review.event_version
- 审核 JSON 快照
- 场次、票档、售票计划各自的 version
风险是：活动主表版本不变，但运营修改了某一个票档售价，审核仍可能按旧版本通过。
审查决定：采用整体审核配置指纹，而不是仅检查 Event 行版本。
提交审核时，规范化生成审核范围内的配置内容，至少涵盖：
- 活动信息。
- 所有有效场次。
- 场馆安排。
- 票档价格、数量及限购。
- 售票计划及销售控制。
- 相关退票规则。
为 ft_event_review 增加：
字段	类型	说明
snapshot_hash	CHAR(64)	审核范围的规范化 SHA-256 摘要
snapshot_schema_version	INT	快照结构版本
待审核期间冻结关键配置，审核通过至发布之前也保持冻结。
发布时重新验证活动及所有关键子配置的有效性，且审核快照与拟发布内容一致。
对于已经上线并发生交易的活动，涉及票价、时间、场次的重大修改不得直接覆盖已发布事实；复杂的线上版本与草稿并行编辑留给 ft_event_revision 的后续增强。
C06：优惠券发行和使用的一致性
当前优惠券设计分为两条链：
领券： 模板额度 → 领取请求 → 用户限领 → 用户券。
用券： 用户券 → 订单锁券 → 支付核销 / 关单释放。
需要保证这些操作不会相互混淆。
审查决定如下：
对象	权威职责
ft_coupon_quota	总发行额度
ft_coupon_user_quota	用户累计领取额度
ft_coupon_claim_request	发券过程及持久化预留凭证
ft_user_coupon	单张券当前状态
ft_coupon_usage	某次订单占用及使用历史
ft_coupon_ledger	发行额度的不可变流水
领券成功后，issued 不能因用户使用优惠券而减少。
订单关闭时，只释放锁券状态，不恢复发行额度或累计领券次数。
支付成功时，用户券和使用记录必须同事务转为 USED。
退款成功后，V1 仍保留 USED，不返券。
必须补强的数据库约束： ft_user_coupon 应以原子状态更新保证单张券当前只能锁定一笔订单，ft_coupon_usage 通过订单唯一约束、使用历史和受控的活跃锁定唯一键防止并发重复核销。

C07：订单、支付和退款的金额口径

ft_order.discount_amount_cent	优惠券减免金额
ft_order.payable_amount_cent	应支付金额
ft_order.paid_amount_cent	实际确认支付金额
ft_payment.amount_cent	支付业务目标金额
ft_refund.amount_cent	本次退款金额

\[
original-discount=payable

\[
paid=payable=payment.amount

V1 全额退款：
\[
refund.amount=payment.amount

C08：业务请求幂等与 Inbox 的职责不同
必须同时保留两层幂等。
层次	权威依据	负责问题
用户操作幂等	ft_purchase_request.request_id	同一次抢票不重复受理
消费事件幂等	ft_message_inbox(consumer_name,event_id)	相同 MQ 事件不重复执行
领域结果幂等	订单、预占、流水等唯一约束	不同事件也不能重复建单或扣减
抢票创建订单之前必须再次检查请求执行权和领域状态，而不能仅因为 Inbox 没有记录就认为可以执行。
对确定性业务失败，抢票请求应写入 FAILED 和明确失败原因，再将消息处理记录提交为完成。
对于因有效租约仍被其他工作者持有而没有执行的消息，不能错误写入“业务完成”的 Inbox 记录。此时需要确保现有处理者或持久化恢复任务仍有责任继续推进。

快照字段	JSON + schema_version
并发版本	BIGINT，按明确状态变更规则递增
特别是库存、订单、支付、退款、优惠券的状态字段，需要维护一份统一的枚举字典，禁止同一含义使用多个不同代码。
订单过期时间、售票窗口、券有效期、演出时间都使用半开区间规则，即开始时间包含、结束时间不包含。
C10：唯一索引与外键必须以业务不变量为依据
不能仅按“高并发表都不要物理外键”的口号设计。
推荐策略：
- 稳定基础实体关系：优先评估物理外键。
- 高并发交易与历史流水：按写入和生命周期选择物理外键或逻辑约束。
- 多态业务关系：使用逻辑关联。
- 核心防重：必须依赖数据库唯一约束。
- 强状态条件：通过锁定和条件更新保证。
- 历史交易实体：禁止无依据的物理删除。
正式建表前，还应检查每个唯一索引的 NULL 语义，尤其是“仅对当前有效状态唯一”的情况。
有一处明确需要修订：ft_coupon_usage 记录同一张券的多次历史锁定时，不能让“历史记录唯一”错误限制后来合法的重新锁券。
此外，ft_refund.UNIQUE(order_id) 意味着 V1 一笔订单最多一项退款申请，包括审核拒绝后也不能新建第二条。因此需要支持同一退款业务的合法复核或重新提交，否则业务会被数据库约束锁死。
C11：对账需要可靠的检查水位线
之前设计的 snapshot_cutoff_at 只是任务元数据，不能自动形成跨表一致快照。
必须明确两种不同的对账模式：
对账模式	适用场景
稳定窗口对账	已完成一段时间的订单、支付和退款
在线状态对账	仍在处理的请求、预占、Outbox
稳定窗口对账使用固定截止范围，并对差异做二次确认。
在线状态对账必须识别合法的中间态，例如正常执行中的消费租约、待确认支付尝试或 Redis 临时资格。
对账任务不能因读取到尚未完成的正常事务阶段，就把它当成账务错误。
补偿任务必须具备独立操作 ID、版本条件、受控执行权和事后重新验证。
C12：通知内容与受众快照
第九批的通知内容与接收记录分离是正确的。
但在发布广播时，不能简单假设当前查询到的所有用户就是“公告发布时的受众”。
建议明确两种投递语义：
类型	投递规则
个人交易通知	精确定位用户，直接创建 Recipient
定向活动通知	基于确定的订单或用户受众集合
全平台公告	可以采用公开公告展示或批量接收分发，二者不能混为一谈
对于要求严格追溯“某时刻应该通知哪些人”的业务，例如演出取消，建议保存固定受众快照。
ft_notification_batch_target 可以作为该功能启用时必须实现的配套实体，而不必现在就加入所有环境的初始表清单。

六、工程落地专项审查
这一部分检查的不是字段是否完整，而是数据库设计能否安全运行。
6.1 模块边界
推荐按照单体内部业务领域隔离持久化责任：
模块	拥有的数据	其他模块访问方式

Event	活动、场次、票档、售票计划	活动查询与规则校验服务
Inventory	库存、预占、流水	库存领域服务
Purchase	请求、限购	抢票服务
Order	订单、明细、操作历史	订单状态服务
Payment	支付、退款与尝试	支付及退款服务
Coupon	营销、发行、用户券与使用	营销服务
Risk	风控规则、限制、事件	风险决策服务

Analytics	统计、对账、补偿	聚合、对账及补偿服务
Messaging	Outbox、Inbox	可靠事件发布与消费
因为是同一个 Spring Boot 应用，一个 MySQL 数据源，可以在应用层设置交易编排服务，协调多个模块的数据修改，使用同一个本地事务提交。
但是不建议业务模块直接到处调用其他模块的 Mapper。
更合适的依赖方式是：
应用编排服务 → 领域服务接口 → 各模块自己维护的数据访问层
这样可以保留模块化单体的边界，同时充分利用本地事务。
6.2 统一事务与重试规范
所有关键业务应满足：
- 事务边界由应用服务明确控制。
- 不在事务中等待 RocketMQ、Redis 网络重试或 SSE。
- 对条件更新受影响行数进行严格检查。
- 对业务唯一键冲突分类处理。
- MySQL 死锁或锁等待超时只进行有限次数的整个事务重试。
- 重试必须使用相同的业务请求号或操作 ID。
- 出现结果不确定时先查权威状态，不直接重做不可逆动作。
- 所有资金与库存变更都保存可追踪操作流水。
对于跨模块事务，需要避免 Spring @Transactional 在内部 self-invocation 下失效的问题，不能只在方法上写了注解就假定事务一定生效。
6.3 状态机完整性
建议建立统一的状态转换契约文档，至少列出：
业务实体	必须禁止的非法转换
PurchaseRequest	SUCCEEDED → FAILED
Reservation	CONFIRMED → RELEASED
Order	PAID → CLOSED
Payment	SUCCEEDED → FAILED
Refund	SUCCEEDED → PROCESSING
UserCoupon	USED → AVAILABLE（V1）
CouponClaimRequest	SUCCEEDED → FAILED
Outbox	SENT → PUBLISHING
TicketEntitlement	REVOKED → ACTIVE（V1）
数据库 CHECK 适合验证当前行合法状态，不会自动知道前一状态是什么。状态转换合法性仍然需要领域服务、条件更新、唯一约束与必要的审计记录配合。

七、发现的其他三个实现风险
除了前面的 16 项审查问题，还有三个需要在具体模块开发时重点验证的细节。
7.1 场次容量不能只验证初始票档数量
前面要求：
\[
\sum 票档初始数量\leq 场次可售容量
\]

但如果运营后来修改库存或增发票量，仅检查 initial_quantity 已经不够。
必须保证所有票档当前核定发行总量满足场次容量限制。增发审批也必须在并发下保护该场次的容量预算，不能让两个票档同时增发而合计超额。
7.2 订单支付期限与消息延迟存在差异
RocketMQ Delay 只是触发关单检查，不是订单过期的权威依据。
即使延迟消息晚到 30 秒，服务端也不能因此自动允许已经到期的订单继续支付。
订单 expire_at 才是业务截止时间，支付和关单应使用同一规则判断。
7.3 统计表的净收入可以为负数
某一天可能没有新支付，但发生了前一天订单的退款。
因此：
\[
当日净模拟收入=当日成功支付-当日成功退款
\]

结果可以为负。
各支付、退款金额字段仍然非负，但计算得到的净额不能增加非负约束。

测试场景	必须满足的结果
10,000 次并发抢 100 张票	最终已占用容量不超过 100
相同 requestId 重复提交	不重复创建订单及预占
不同请求并发使用同一张券	最多一笔有效订单锁券
