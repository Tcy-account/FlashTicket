FlashTicket 业务需求设计 07：优惠券与营销活动模块
Coupon & Promotion Management · V1.0 · 高并发营销业务
本模块负责 FlashTicket 平台的优惠券创建、限量抢券、异步发券、优惠计算、订单锁券、支付核销、关单返券与退款处理。
它是继票务库存之后，第二个能够重点展示 Redis Lua、RocketMQ、MySQL 并发事务和业务幂等能力的模块。
本轮继续只设计业务需求、规则、状态机、数据实体和接口，不编写 Java 代码或数据库 DDL。

4.2 优惠券叠加规则
为了让第一版的订单金额模型保持清晰，我建议：
- 一笔订单最多使用一张优惠券。
- 不允许两张优惠券叠加。
- 不与其他订单级促销叠加。
- 优惠金额不能超过订单商品金额。
- 使用条件按优惠前商品金额计算。
- 不允许负金额订单。
- 优惠券不能兑换现金，也不能转赠其他用户。
五、限量抢券与异步发券
这里设计两套实现，和前面票务库存模块保持一致。
方案 A：MySQL 直接发券
作为正确性基线。
1. 用户提交唯一领券请求 ID。
2. 检查活动有效期、用户资格和领券限制。
3. 在 MySQL 事务内原子扣减发行配额。
4. 创建用户优惠券与发行流水。
5. 更新领券请求为成功，返回券信息。

优点是正确性比较容易验证，缺点是高并发情况下同一张模板的发行计数可能成为数据库热点。
方案 B：Redis Lua + RocketMQ 异步发券
用户点击立即领券


登录、活动资格、用户限流


MySQL 可靠受理请求
请求记录 + 恢复信息


Redis Lua 发放领券资格
额度检查 · 请求去重 · 用户限领


持久化预占状态与 Outbox
失败可恢复或释放额度


RocketMQ 异步发券


MySQL 确认发行 + 创建用户券


Redis Lua 能原子完成额度检查与扣减，但无法自动把 Redis、MySQL 和 RocketMQ 组成一个原子事务。

Docs



因此：
- Redis 领券资格成功，不等于用户券已经发放。
- MySQL 成功创建用户券后，才算真正领券成功。
- 请求重复不能重复减少 Redis 额度。
- Redis 临时资格未落库时，必须保留可恢复状态。
- Redis 重启时，应暂停新发券资格发放，安全重建剩余额度。
这与抢票库存模型很相似，但优惠券发行额度和票务库存是两个独立的业务账本。
六、优惠券发行额度模型
建议优惠券模板维护独立的三态发行账本：
\[
总发行额度=剩余额度+预留额度+已发放额度
\]

字段	作用
total	当前核定发行总量
available	仍可发放的数量
reserved	已取得资格但尚未落库的额度
issued	已经成功生成的用户券数量
与门票库存不同的是：
用户领取优惠券后，即使这张券被使用或过期，也不自动恢复模板发行额度。
例如模板发行 1000 张，用户成功领取 1000 张，其中 200 张已经使用，100 张已过期，这个模板仍然算发行了 1000 张。

七、用户优惠券生命周期
这里需要区分两种不同状态：
- 券本身的生命周期：尚未使用、被订单锁定、已经使用、已过期、已作废。
- 领券请求的生命周期：排队中、处理中、发放成功、失败、恢复中。
7.1 用户券状态机
AVAILABLE · 待使用


LOCKED · 订单已锁券
优惠券仅属于当前未支付订单


USED
支付成功，正式核销


AVAILABLE
关单后符合规则则返券



未锁定的券可以到期变为 EXPIRED，也可以被运营依法依规则作废为 VOID。锁定中的券是否超期，必须在订单终结时再判定。
7.2 状态转换规则
原状态	触发业务	目标状态
不存在	发券成功	AVAILABLE
AVAILABLE	订单创建并占用	LOCKED
AVAILABLE	有效期结束	EXPIRED
LOCKED	订单支付成功	USED
LOCKED	未支付订单关闭，券仍有效	AVAILABLE
LOCKED	未支付订单关闭，券已过期	EXPIRED
USED	退款成功	保持 USED（V1）
AVAILABLE	合规作废操作	VOID
订单未支付关闭后可以返券；已支付退款后默认不返券。
这与之前已经确定的“退款成功后门票不自动重新上架”规则保持一致。
7.3 特别重要：优惠券过期时正在支付怎么办？
例如优惠券在 20:00 过期，用户在 19:59:50 创建订单，支付截止时间是 20:14:50。
推荐规则：
只要锁券发生在券有效期内，订单可以在自己的支付期限内使用该优惠。
也就是说，券过期时间影响新订单能不能锁券，不应在已经合法锁券的订单支付时重新判定券是否过期。
订单支付成功则核销；未支付关闭则根据返券时刻决定是否恢复可用。
八、优惠券如何与抢票订单结合？
这是 FlashTicket 必须设计清楚的地方。
我们此前已经确定：
- 一笔订单对应一个场次、一个票档。
- 抢票请求经 RocketMQ 异步处理。
- 库存预占与创建订单处于同一个 MySQL 事务。
- 支付期限 15 分钟。
现在增加优惠券后，推荐：
抢票请求提交时选择用户优惠券；异步创建订单时正式锁券。
用户选择票档、数量、优惠券


创建抢票请求
持久化 selectedCouponId，不接收客户端计算的优惠金额


RocketMQ 异步消费
重新检查资格、优惠券所有权和有效性


同一个 MySQL 本地事务
1. 获取抢票请求处理权及限购资格
2. 条件锁定用户优惠券
3. 计算并固定优惠金额
4. 预占门票库存
5. 创建订单及价格快照
6. 更新请求终态与 Outbox 事件


订单待支付 · 优惠券 LOCKED


如果任意操作失败，同一个 MySQL 事务整体回滚。
对于已经执行的 Redis 临时抢票预占，仍然按照库存模块的恢复协议处理，不能认为 MySQL 回滚会同时回滚 Redis。
一个需要提前确定的业务选择
当用户选中的优惠券在排队期间被其他订单使用或已过期时，默认本次抢票失败，不自动按原价创建订单。
原因是自动去掉优惠券会改变用户原本确认的价格。后续可以设计用户明确授权的“优惠失效后原价购买”选项，但第一版先不做。

十、支付、关单与退款的优惠券处理
这部分必须与之前的订单状态机保持一致。
交易事件	原券状态	操作	最终状态
订单创建	AVAILABLE	锁券	LOCKED
支付成功	LOCKED	正式核销	USED
用户取消未支付订单	LOCKED	释放券，判断有效期	AVAILABLE / EXPIRED
超时关单	LOCKED	释放券，判断有效期	AVAILABLE / EXPIRED
支付失败但订单仍有效	LOCKED	保留当前订单锁定	LOCKED
退款申请	USED	暂不变更	USED
退款审核通过	USED	暂不变更	USED
退款成功	USED	第一版不返券	USED
最重要的是订单状态、优惠券状态、库存状态必须在同一个 MySQL 事务内进行相关终态转换。
例如超时关单要同时完成订单关闭、库存释放、限购释放、优惠券解锁、库存与订单流水及 Outbox 事件持久化。
如果优惠券解锁失败，不能让订单已经关闭、库存已经释放，却遗留一张永久锁定的券。应使整个本地事务回滚并进行可靠重试。
十一、数据库实体规划
第一版建议规划七张核心营销表。
表名	主要职责	重要约束
ft_campaign	营销活动主体	活动状态、时间范围
ft_coupon_template	优惠券模板与规则	模板 ID、规则版本
ft_coupon_quota	模板发行额度账本	template_id 唯一、非负额度
ft_coupon_claim_request	领券请求、状态和恢复记录	request_id 唯一
ft_user_coupon	用户持有的优惠券	userId、templateId、状态、有效期
ft_coupon_usage	订单锁券和核销记录	同一券不能同时绑定多个有效订单
ft_coupon_ledger	额度调整、发券、返券、核销审计	operation_id 唯一
还需要一张用户领取额度计数表，如 ft_coupon_user_quota，保证同一用户的并发领取限制。它可以作为第八张表，也可以由经过严格验证的唯一约束与用户券记录模型实现，但不能只依赖普通查询计数。
数据库约束
- 模板发行数量不得超过核定总额度。
- 已发行用户券不得重复创建。
- 同一领券请求只能完成一次发券。
- 用户领券数不得超过模板的用户限领额度。
- 一张用户券只能被一个有效订单锁定。
- LOCKED → USED 或 LOCKED → AVAILABLE/EXPIRED 必须是互斥终态转换。
- 所有发行额度变化与用户券创建应形成可追踪的账本操作。
优惠券重复核销、限领并发绕过等都属于典型业务逻辑竞态，不能通过简单的“先查询、再更新”来保证正确性。

十三、RocketMQ 消息规划
营销模块需要独立的 Topic，避免和票务抢票消息混用。
Topic	消息类型	Consumer Group	用途
ft-coupon-claim	Normal	ft-coupon-claim-cg	异步领取并发放用户券
ft-coupon-event	Normal	ft-coupon-event-cg	优惠券发放、核销、返券事件
建议业务事件包括：
- COUPON_CLAIM_REQUESTED
- COUPON_ISSUED
- COUPON_CLAIM_FAILED
- COUPON_LOCKED
- COUPON_USED
- COUPON_RELEASED
- COUPON_VOIDED
这里要区分业务事件通知与核心状态修改：
同一 MySQL 数据源下，订单支付成功与优惠券核销应直接在同一个数据库事务内完成。RocketMQ 事件只用于后续通知、统计、审计扩展等业务，不承担这两个核心状态之间的最终原子性。
RocketMQ 普通消息适合这种独立业务事件的异步传递，但重复消费仍然需要业务幂等。

十五、关键异常与补偿规则
异常场景	处理原则
同一用户并发领券	原子限领与请求幂等
Redis 扣额度成功、MySQL 写入失败	保留可恢复记录，确认失败后幂等归还额度
RocketMQ 重复投递	用户券唯一约束、Inbox 幂等
Redis 重启丢失预占状态	关闭发券入口、隔离旧代次、核对后重建
订单重复创建	同一抢票请求只锁券一次
用户在两笔订单中同时使用同一券	只有一个事务能成功锁券
锁券成功但订单事务回滚	锁券回滚，券仍可用
支付成功与关单竞争	核销和返券只能出现一个合法结果
关单时优惠券已过期	转为 EXPIRED，不能恢复可用
退款完成后重复通知	用户券仍保持已使用，不重复返券
优惠券模板暂停或取消	禁止新领取；已发券按公告和规则独立处理
对账发现发行额度不一致	生成异常记录，暂停新发券，不直接覆盖账本
还有一个关键业务约束：同一模板不能在已有有效用户券时，随意改变优惠规则及适用范围。 应采用版本或快照，确保既有用户的权益可解释、可追溯。

十八、优惠券与营销活动模块 V1.0 定稿
FlashTicket 营销业务方案


营销模式： 限时抢券、指定演出优惠；新用户专享后续扩展。
券种： P0 满减券，P1 折扣券。
发行模式： MySQL 额度原子扣减作为正确性基线；RocketMQ 异步发券；Redis Lua 作为后续高速准入优化。
用户限领： 模板配置每人上限，默认每人一张，MySQL 原子约束兜底。
使用规则： 一笔订单最多使用一张优惠券，订单创建时正式锁券。
状态机： AVAILABLE → LOCKED → USED，未支付关单按有效期释放。
支付与退款： 支付成功核销；退款成功默认不返券。
订单金额： 服务端计算并保存优惠前金额、优惠金额和最终应付金额。
可靠性： Redis Lua + MySQL 事务 + RocketMQ Outbox/Inbox + 幂等 + 补偿对账。

至此 FlashTicket 已经完成七个主要业务模块的需求设计：用户与账号、演出与场次、库存预占、抢票排队、订单状态机、模拟支付退款、优惠券营销。
