FlashTicket 业务需求设计 03：库存与票档预占模块
Inventory & Reservation · V1.0 · 高并发核心业务模块
这是 FlashTicket 最值得深入研究的模块，也是整个项目在互联网大厂 Java 后端实习面试中的主要技术亮点。
前面我们已经确定：
- 票务模式：第一版只支持不指定座位的数量型票档。
- 数据库：MySQL 8.4 LTS，InnoDB，默认 REPEATABLE READ。
- 缓存：Redis 7.4，Lettuce、Redisson、Lua。
- 消息队列：RocketMQ 5.x，Transactional Outbox + Inbox。
- 单体架构：Spring Boot 3.5.x，一个业务应用，按领域模块划分。
本模块要实现的目标是：
在高并发抢票、超时取消、消息重复、进程崩溃和 Redis 故障等情况下，保证库存不超卖、不重复释放、可恢复、可对账。

二、库存模型：采用三态账本
建议采用以下模型：
\[
\text{总库存}=\text{可售库存}+\text{预占库存}+\text{已售库存}
\]

字段	含义	何时变化
total	当前核定票量	合法增减库存时
available	尚未被占用的票量	预占减少，释放增加
reserved	已由 MySQL 确认预占的票量	预占增加，确认或释放减少
sold	已完成支付确认的票量	确认已售时增加
version	数据版本	每次库存账目变化递增

必须保证的账目约束
1. 所有库存值必须大于或等于零。
2. available + reserved + sold = total 必须始终成立。
3. 一个成功预占只能确认或释放一次。
4. 确认已售的票不能再使用普通预占释放操作。
5. 运营调整库存必须形成独立流水，不能直接覆盖计数。
6. Redis 的预占状态不直接等同于 MySQL 的 reserved。
特别说明：上面的库存等式是 MySQL 已提交账本的约束。Redis 中暂时拿到资格但尚未落库的预占，需要单独记录，不能立即混算到数据库账本里。

四、库存预占的状态机
不能仅通过 Redis Key 是否存在来判断预占有效性。
建议每次预占都关联唯一 requestId 和 reservationId。
INIT / 待处理请求


REDIS_HELD
Redis 资格已预占，尚未确认数据库预占


RESERVED
MySQL 预占已提交，等待支付结果


CONFIRMED
支付成功，转已售


RELEASED
取消、超时或失败释放



这是主要成功路径的简化图；Redis 预占失败、数据库提交失败或结果不确定时还存在 REJECTED、RELEASING、RECOVERING 等状态。
状态转换规则
原状态	允许动作	目标状态
INIT	Redis 预占成功	REDIS_HELD
INIT	库存不足 / 资格不符	REJECTED
REDIS_HELD	MySQL 预占成功	RESERVED
REDIS_HELD	确认失败、执行补偿	RELEASING → RELEASED
RESERVED	支付正式确认	CONFIRMED
RESERVED	订单取消 / 过期	RELEASING → RELEASED
处理中	操作结果暂不确定	RECOVERING
CONFIRMED	重复确认	幂等返回
RELEASED	重复释放	幂等返回
这些状态应由库存模块统一管理。
另外，REDIS_HELD 是高速预占阶段的状态，不建议将它和数据库中的已预占数量直接等同。实际实现中，需要使用请求流水或恢复记录，使这个中间状态在服务重启后仍能识别。
五、数据库模型设计
本阶段建议库存中心使用三张核心表、一张 Redis 预占恢复辅助表（可以复用抢票请求表）。
表名	职责	核心字段
ft_inventory	库存总账	tier_id、total、available、reserved、sold、version
ft_reservation	持久化预占记录	reservation_id、request_id、tier_id、quantity、status、expire_at
ft_inventory_ledger	库存变化流水	id、operation_id、tier_id、reservation_id、operation、quantity
ft_purchase_request	请求受理及 Redis 预占恢复锚点	request_id、user_id、status、last_error、updated_at
其中 ft_purchase_request 归属于抢票模块，但库存模块可以通过约定的服务接口查询相关恢复状态。
数据唯一性要求
- ft_inventory.tier_id 唯一。
- ft_reservation.request_id 唯一。
- ft_inventory_ledger.operation_id 唯一。
- 每条流水记录明确操作方向、数量和对应的预占记录。
- 更新库存与更新预占状态、插入库存流水，在同一个 MySQL 本地事务中完成。
对于已经存在的预占，重复请求只返回原有状态，不允许再扣一次库存。
采用 MySQL 条件更新作为底层兜底
MySQL InnoDB 提供行级锁与事务机制，适合通过条件更新保证库存账本不会被多个并发事务同时错误修改。

库存预占的概念性操作为：
\[
available \leftarrow available-q
\]

\[
reserved \leftarrow reserved+q
\]

其中 \(q\) 是此次购买数量。
只有当可售库存不少于 \(q\)、预占仍允许进行且本次业务事务能够完成时，才允许提交。version 用来记录账目变更和辅助并发控制，但不要求对已经使用安全条件更新的库存操作再额外使用一次版本比较。
六、Redis 高速预占设计
这是区别于 MySQL 基线版本的第二套实现。
Redis 主要负责：
1. 在大量用户抢票时快速排除库存不足请求。
2. 原子处理同一请求的重复预占。
3. 减轻瞬时流量直接冲击数据库的压力。
4. 在有限并发和容量控制下向后端放行购票请求。
Redis Key 规划
Key	类型	用途
ft:stock:{tierId}	String	Redis 可发放的预占资格余额
ft:holds:{tierId}	Hash	记录该票档的临时预占令牌及数量
ft:stock:meta:{tierId}	Hash	当前初始化版本、重建代次和销售状态
ft:limit:purchase:{tierId}	String	票档级入口限流计数
ft:inventory:rebuild:{tierId}	String	重建操作协调标记
{tierId} 在实际命名时应替换成真实票档 ID，例如 ft:stock:{20001}。
三个需要由同一个 Lua 脚本处理的库存 Key 使用相同 Hash Tag，以便未来迁移到 Redis Cluster。Redis Cluster 的多 Key 原子操作要求它们位于同一 Hash Slot。

Lua 负责哪些检查？
原子预占操作：
- 当前 Redis 库存代次是否有效。
- 票档是否允许发放新的预占资格。
- 同一 requestId 是否已经存在预占。
- 剩余资格是否大于或等于购买数量。
- 同时扣减资格余额并记录预占令牌。
Redis 官方保证 Lua 脚本在单次执行期间具有原子性，但脚本执行期间会阻塞 Redis 其他命令，因此不应进行复杂循环或耗时计算。

一个关键区别：库存总账与 Redis 准入预算
假设总库存 100 张，Redis 已经发放 10 张预占资格，其中 MySQL 仅确认 6 张。
此时：
项目	数值
MySQL 总库存	100
MySQL 可售	94
MySQL 已确认预占	6
Redis 尚未落库预占	4
安全的剩余可发放资格	90
因此在存在未落库预占时，不能直接把 MySQL 的 available = 94 覆盖到 Redis 库存 Key。否则可能重新发放已经被 4 个在途请求占用的资格。
在稳定的同步检查点下，若 Redis 准入预算能与数据库确认状态一一映射，可以将其理解为：
\[
可发放预算=MySQL可售-未落库的有效预占
\]

但真正重建前，还必须确保没有旧代次请求继续提交，并处理正在释放、尚未确认结果的操作。
Redis 不再只是“缓存一下库存”，而是一个带有在途预占记录的快速准入控制层。
七、推荐的两阶段实现方案
这是我建议你在项目中保留的两条技术路线。
方案 A：MySQL 事务直接预占
基线版本

抢票请求已持久化

MySQL 库存条件更新

预占记录 + 库存流水，同一事务提交

通知订单模块创建待支付订单
优势是状态较少、正确性容易证明；不足是极热票档存在 MySQL 行锁竞争。

方案 B：Redis Lua + MySQL 确认
优化版本

可靠受理抢票请求

Redis Lua 发放预占资格

MySQL 预占确认 + 请求状态持久化

Outbox + RocketMQ 驱动订单后续处理
优势是可以快速拦截无库存请求；额外复杂度来自跨 Redis 与 MySQL 的状态协调。


采用方案 B 时，要承认一个工程事实： 如果所有成功抢到资格的请求最终仍然更新同一条 MySQL 库存记录，数据库热点竞争并不会彻底消失。Redis 可以削减无效请求和控制入场速率，但不自动消除成功订单的持久化瓶颈。
因此先实现 A，再实现 B 并进行压测对照，比直接上 Redis 更有学习和面试价值。
八、预占、确认和释放的业务规则
8.1 预占 Reserve
输入： 请求 ID、票档 ID、用户 ID、购买数量。
必须满足：
- 抢票请求已被可靠受理。
- 活动、场次、票档满足销售规则。
- 购票数量合法。
- 当前没有重复的有效预占。
- 可售资格和持久化库存均满足要求。
成功结果： 生成预占记录，状态为 RESERVED，附带 expireAt。
失败结果： 明确区分库存不足、销售暂停、重复请求及暂时性系统故障。
不得把网络超时直接判定为预占失败，因为远端操作可能已经执行成功。
8.2 确认 Confirm
触发： 订单的模拟支付达到业务上认可的最终成功状态。
规则：
- 仅 RESERVED 可以转换成 CONFIRMED。
- 与订单支付状态变化保持一致的事务边界或可靠协调。
- reserved 减少，sold 增加。
- 重复确认不重复增加已售库存。
- 已释放的预占不能被普通确认操作重新确认。
由于订单、支付、库存同处一个 MySQL 数据库，最终支付确认与数据库库存账目转换优先采用同一个本地事务。事务提交后再通过 Outbox 通知其他非关键业务，避免把本可原子完成的核心账务操作不必要地拆成跨消息事务。
8.3 释放 Release
允许释放的情形：
- 用户取消待支付订单。
- 未支付订单超过有效期。
- 订单创建确定失败。
- 抢票受理后确认业务不满足要求。
- Redis 预占后 MySQL 确认失败。
禁止释放的情形：
- 已支付且已确认的订单直接触发普通释放。
- 同一次预占第二次释放。
- 订单只是 HTTP 请求超时、尚不能确认真实处理结果。
- 预占令牌与当前库存代次不匹配。
已售票若以后允许退款后重新销售，必须走独立的退票回补业务，不得复用未支付订单的预占释放逻辑。
8.4 超时处理
建议：
超时类型	建议值	作用
Redis 暂存预占处理时限	初始 30 秒（可调）	识别长时间未落库的预占
待支付订单有效期	15 分钟	到期关闭订单
恢复扫描间隔	10–30 秒（可调）	发现需要恢复的请求
库存对账周期	开发环境 1–5 分钟	发现状态不一致
这里的 30 秒是“需要检查和恢复”的业务时限，不是 Redis 一到期就直接执行 INCR 返还库存。
而且未创建订单阶段与订单待支付阶段使用不同的到期时间；订单创建后，支付截止时间应成为对应预占的业务到期依据。
九、异常恢复与补偿机制
这一部分决定方案是否能真正可靠。
故障	可能的问题	恢复策略
Redis Lua 成功后 Java 进程崩溃	资格被占用，但 MySQL 尚未确认	基于持久化请求和 Redis 令牌恢复，确认或安全释放
Redis 预占成功，数据库不可用	在途资格长期占用	限流或暂停新请求，待数据库恢复后重试或补偿
MySQL 已提交，但客户端收到超时	重试可能重复操作	先通过 requestId 查询持久化结果，幂等返回
数据库确认失败	Redis 资格可能未归还	进入释放补偿流程，按预占令牌执行
RocketMQ 无法发送	订单后续事件未发布	Outbox 持久化，恢复后重试
消费者重复处理	可能重复预占或释放	Inbox + 唯一约束 + 状态条件更新
Redis 重启丢失状态	准入预算和预占标记不可信	关闭准入、隔离旧代次、恢复请求、重建预算
销售中运营增加票量	Redis 和 MySQL 容量变化不同步	先持久化变更，再按版本可靠更新 Redis
销售暂停时仍有在途请求	可能出现暂停后新订单	按明确的准入时刻和配置版本处理在途请求
特别重要：Redis 故障恢复方案
推荐使用票档销售代次（generation）+ 恢复屏障。
Redis 库存状态失效或无法确认


关闭该票档的新预占入口


阻止旧代次请求继续确认库存
使用数据库持久化的代次和状态条件进行校验


扫描和终结在途预占
完成、释放或标记需进一步恢复


依据 MySQL 总账及有效预占重建 Redis


检查通过后开放新的销售代次


仅用 Redisson 锁包围 Redis 重建过程并不充分，因为旧请求可能持有之前发放的资格继续执行。需要由 MySQL 侧的代次校验或等效的恢复屏障阻止旧操作生效。
这也意味着，当系统不能安全判断可售资格时，宁可暂时停止该票档销售，也不要冒险多发库存。
十、库存对账与运营调整
库存对账应分成三个层次。
对账层次	核验内容	处理原则
库存总账	total = available + reserved + sold	出错立即告警，禁止直接覆盖修正
预占明细	有效预占数量与 reserved 是否一致	定位重复、遗漏、异常状态
交易一致性	已售库存与有效订单、支付确认是否匹配	识别订单账务问题
Redis 准入状态	Redis 剩余额度与未落库预占是否一致	异常时关闭入口并重建
库存人工调整
建议 P1 增加以下规则：
- 只有具备 inventory:adjust 权限的人员可以提交库存调整。
- 增减数量和调整原因必填。
- 负向调整不得使库存低于已经预占与已售的数量。
- 已发布销售中的调整需要操作审计和版本变更。
- P1 支持双人审核，防止运营人员单独修改重要库存。
- 发现异常不能直接手动把 Redis Key 改成某个数。
对于有真实客户交易的系统，库存流水不仅用于显示操作历史，还承担故障审计与重建依据的作用。

十四、库存模块 V1.0 最终决策
FlashTicket 库存与票档预占模块定稿


票务模式： 第一版数量型库存，不指定座位；按票档独立核算。
核心账本： MySQL available / reserved / sold 三态库存。
预占状态： 请求受理、Redis 临时预占、数据库确认预占、确认已售、释放与异常恢复。
并发保障： MySQL 条件更新 + 唯一约束 + 本地事务 + 幂等状态机。
高速准入： Redis Lua 实现快速资格预占，必须保留可识别的在途请求和 Redis 预占预算。
异步协调： MySQL Outbox + RocketMQ，消息重复由业务幂等处理。
异常恢复： 数据库对账、超时补偿、销售代次、Redis 安全重建。
实现策略： 先 MySQL 基线，再 Redis 优化，并以正确性及压测数据评估方案。
