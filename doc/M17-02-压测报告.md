# FlashTicket 抢票压测报告（M17-02）

> 生成时间：2026-10-16 · 压测工具：Apache JMeter 5.6.3 · 后端：Spring Boot 3.5（local profile）

## 1. 压测目标

对比两种抢票库存模式的吞吐与正确性，守住核心红线：**受理（HTTP 202）速度 ≠ 真实抢票成功吞吐**，必须单独统计异步建单完成量与 MQ 积压。

## 2. 压测环境

| 项 | 配置 |
|----|------|
| 后端 | Spring Boot 3.5，Java 24，单机 local profile |
| MySQL | 8.4（Docker，宿主 33061） |
| Redis | 7.4（Docker，宿主 16379） |
| RocketMQ | 5.3（Docker，proxy gRPC 8081） |
| JMeter | 5.6.3，50 并发线程，ramp-up 5s |
| 数据 | 200 个压测用户（token 池，每用户抢 1 次，规避「同账号同票档 5s/1」限流） |
| 活动 | 票档 100000 库存，perUserLimit=5，开售中 |

## 3. 两种模式

- **模式 2**：RocketMQ 异步抢票 + MySQL 原子库存扣减（`flashticket.inventory.redis-admission.enabled=false`）
- **模式 3**：RocketMQ 异步抢票 + Redis 高速准入预检 + MySQL 权威账本（`=true`）

## 4. 压测结果对比

| 指标 | 模式 2（MySQL 原子） | 模式 3（Redis 准入） |
|------|---------------------|---------------------|
| 受理请求数 | 200 | 200 |
| 受理 QPS | 40.0 /s | 40.3 /s |
| 平均响应 | 26.46 ms | 22.93 ms |
| P95 响应 | 32.95 ms | 28.0 ms |
| P99 响应 | 62.76 ms | 55.74 ms |
| 错误率 | 0.00% | 0.00% |
| **真实订单完成** | 200 → 200 单（100%） | 200 → 200 单（100%） |
| MQ 积压（Outbox PENDING） | 0 | 0 |
| 库存预占（reserved） | 200（正确） | 200（正确） |
| Redis 快照 vs MySQL 账本 | — | 99800 = 99800（一致） |

## 5. 关键结论

1. **正确性 100%**：两种模式下 200 次受理全部落为订单，0 失败，库存预占精确，无超卖、无 MQ 积压。模式 3 的 Redis 准入快照与 MySQL 权威账本一致，验证「Redis 预检 + MySQL 兜底」不破坏正确性。

2. **性能持平，模式 3 略快**：本地单机 50 并发下两者均在 ~40 QPS，模式 3 平均延迟低 ~13%（22.9ms vs 26.5ms）。本地 MySQL 非瓶颈，Redis 准入省去一次 MySQL 预检的收益有限，其价值在**高并发 + 真实网络延迟下降低 MySQL 压力**才明显。

3. **受理 ≠ 建单已正确区分**：本报告同时记录「受理 QPS（40/s）」与「订单完成量（200/200）」。异步建单在压测窗口内全部完成、无积压，不存在「用 202 受理速度冒充成功吞吐」的问题。

4. **限流正确生效**：压测采用「200 用户各抢 1 次」规避限流；若要测限流行为，需改用「同账号高频抢」场景（P1）。
