# FlashTicket 前端 UI/UX 设计与开发规范 V1.0

## 一、项目背景

项目名称：FlashTicket

中文定位：高并发演出抢票与票务管理平台

品牌 Slogan：每一场热爱，都值得奔赴。

FlashTicket 是一个包含用户端和运营管理端的完整票务平台。用户可以注册登录、浏览演出、选择场次和票档、抢票排队、创建订单、模拟支付、申请退款、领取优惠券和查看消息。

运营人员可以管理演出、场馆、场次、票档、库存、订单、退款、营销活动、风控规则和运营数据。

本项目采用前后端分离架构，Java 后端由开发者本人负责，前端全部由 AI 负责设计和开发。

**核心要求：前端不仅要美观，还必须具备真实的 API 对接能力，让后端开发者直接通过浏览器验证自己实现的业务功能，不依赖 Postman 或 curl。**

## 三、全局视觉风格

FlashTicket 整体采用现代、简约、年轻、精致、有品质感的视觉语言。

参考方向：

- Linear：克制、专业的视觉细节
- Vercel：简洁、清晰的页面结构
- Apple：排版、留白与交互细节
- 现代演出和音乐票务平台：强调海报与现场氛围

不要直接复制其他品牌的页面。

设计原则：

1. 不使用传统、老旧的后台管理模板。
2. 不使用大量渐变背景。
3. 不使用夸张的阴影和发光效果。
4. 不堆砌卡片、边框和装饰。
5. 不使用过度圆润的儿童化组件。
6. 不采用赛博朋克、霓虹灯或游戏化 UI。
7. 页面要有明确的信息层级和呼吸感。
8. 用户端与管理端保留统一品牌识别，但采用不同布局。
9. 所有页面必须支持响应式。
10. 视觉效果必须服务于业务操作，而不是纯展示。

整体风格定义为：

**Modern Minimalism + Premium Ticketing + Subtle Technology**

即现代极简、品质感票务设计和适度科技感。

## 六、布局与组件规范

### 圆角

- 页面主要卡片：12–16px
- 输入框：8–10px
- 普通按钮：8–10px
- 弹窗：14–16px
- 图片卡片：12–16px

不要所有组件都使用胶囊形状。

### 阴影

卡片优先使用浅边框和轻微阴影。

鼠标悬停时可适度提升阴影或位置，但动画要克制。

### 间距

使用 4px 或 8px 基础间距系统。

常用间距：

8 / 12 / 16 / 24 / 32 / 48px。

同一页面保持统一的布局节奏。

### 动画

- 按钮：120–180ms
- 卡片 Hover：150–220ms
- 弹窗：180–250ms
- 页面状态过渡：200–300ms

避免大幅缩放、复杂飞入及不必要的动画。

尊重用户系统的减少动态效果设置。

- 不使用凌乱的背景装饰

- 登录表单视觉居中，宽度约 380–420px。
- 输入框和按钮高度约 44–48px。
- 页面避免过度装饰。
- 登录错误在对应位置明确展示。
- 登录期间按钮显示 Loading。

### 9.2 用户注册页

与登录页保持统一布局和品牌风格。

表单包含：

- 用户名
- 邮箱
- 邮箱验证码
- 密码
- 确认密码
- 注册按钮
- 已有账号，立即登录

表单校验应能显示：

- 用户名格式不正确

- 验证码错误或过期
- 用户名或邮箱已注册

校验规则以实际后端接口契约为准。

保持同样的表单设计语言。

根据后端实际实现阶段逐步接入，不自行虚构成功结果。

### 9.4 登录后的初始首页

在演出模块尚未开发时，不需要制作大量无法使用的假功能。

- 顶部品牌导航

## 十、前后端 API 对接规范

Java 后端负责定义真实 API。

AI 前端负责实现：

- Axios 实例
- 统一响应解析
- 错误码展示
- Token 刷新
- 登录态维护
- 路由守卫
- API 类型定义
- 请求 Loading
- 请求取消
- 防重复提交

Access Token 存储于内存。

Refresh Token 使用 HttpOnly Cookie，不在 localStorage 保存 Refresh Token。

如果刷新接口依赖 Cookie，需要正确配置请求凭据与本地代理；生产环境还必须考虑 Secure、SameSite、CSRF 与跨域策略。

优先根据后端 OpenAPI 生成 TypeScript API 类型，减少前后端字段不一致的问题。

不能在前端直接修改后端业务状态来模拟成功。

## 十一、开发专用 API Lab

由于后端开发者不熟悉 Postman 和 curl，必须提供一个仅开发环境可用的 API 调试页面。

建议地址：

`/dev/api-lab`

此页面需要具备：

- 已接入接口列表
- 按业务模块分类
- 请求方法和 URL
- 可编辑测试参数
- 发送请求
- 真实 HTTP 状态码
- 响应耗时
- 脱敏后的响应 JSON
- 错误提示
- 请求 ID 和 Trace ID（如果后端提供）

第一阶段支持：

- 发送邮箱验证码
- 用户注册
- 用户登录
- 刷新登录
- 获取当前用户
- 修改个人信息
- 退出登录

注意：

1. API Lab 仅开发环境提供。
2. 生产构建必须排除调试入口与调试能力。
3. 不记录明文密码、Token、验证码。
4. 不提供绕过身份验证的后端接口。
5. 页面请求必须真实调用后端。
6. 不能用模拟成功响应欺骗开发者。

## 十二、空状态、加载状态与错误反馈

所有业务页面必须包含：

**Loading：** Skeleton、Spinner 或按钮加载状态。

**Empty：** 无数据时展示合理插画或图标，并提供明确说明。

**Error：** 明确区分网络错误、未登录、权限不足、业务失败、服务异常。

**Success：** 操作成功后及时反馈，并刷新相关真实数据。

对于注册、登录和购票等操作，错误信息应清晰但不能泄露账号枚举、安全令牌或内部数据库结构。

页面不要直接展示 Java 异常堆栈。

## 十三、响应式适配

必须覆盖：

- 桌面端：1440px 及以上
- 笔记本：1024–1439px
- 平板：768–1023px
- 手机：小于 768px

用户端必须认真设计移动端体验。

管理端优先桌面端，但小屏时表格、侧边栏、筛选和操作按钮不能严重溢出。

不允许使用固定宽度导致主要内容被裁切。

## 十四、开发方式

请采用渐进式开发，不要一次性实现所有页面。

当前优先顺序：

**阶段一：** 前端工程初始化、设计系统、用户登录页、注册页、基础布局、API Lab。

**阶段二：** 接入真实账号接口、登录状态维护、个人中心、退出、找回密码。

**阶段三：** 管理端登录、用户和权限管理。

**阶段四：** 演出展示、活动和场次管理。

其余业务功能在后端开发对应接口时，再逐步增加页面。

每完成一个业务功能，都必须通过前端实际操作验证真实 Java 后端接口。

## 十五、AI 前端开发的强制要求

1. 保持视觉规范统一，不同页面不要随意变更配色和圆角。
2. 优先考虑真实产品的用户体验。
3. 代码采用 Vue 3 + TypeScript，保持组件职责清晰。
4. 不要大量创建没有实际价值的封装。
5. 不要擅自修改后端 API 契约。
6. 不要提前构造大量虚假业务数据。
7. 不要在正常业务页面展示调试 JSON。
8. 调试功能只能放在开发专用页面。
9. 对应后端接口不存在时，明确说明未实现。
10. 不允许把网络错误伪装成业务成功。
11. 不允许将密码或认证 Token 写入浏览器日志。
12. 保持用户端与管理端视觉风格的一致性和适度差异化。
13. 所有界面文案优先使用简体中文。
14. 组件要有键盘操作、焦点状态和基本无障碍支持。
15. 新增功能不能破坏已有登录流程与页面交互。
