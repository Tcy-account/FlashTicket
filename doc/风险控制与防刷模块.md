FlashTicket 业务需求设计 08：风险控制与防刷模块
推荐方案 V1.0
Risk Control & Anti-Abuse · 业务与架构设计

本模块负责保护 FlashTicket 的登录、抢票、领券、订单和模拟支付接口，防止恶意请求占用系统资源、绕过业务限制或影响正常用户购票。
它是 FlashTicket 第三个重点展示高并发能力的模块：
- 库存中心： 解决超卖和库存一致性。
- 抢票中心： 解决异步排队和流量削峰。
- 风控中心： 解决恶意流量、资源保护、异常请求和服务降级。
我们不做复杂的机器学习风控平台，而是实现一套基于规则引擎、Redis Lua、多维限流、风险评分和分级处置的 Java 风控系统。
本轮只设计业务需求、数据模型、状态机、接口及验收标准，不编写代码。
一、风控模块的核心定位
首先明确：风控不是只有限流。
能力	要解决的问题	示例
请求限流	请求频率过高	单用户每秒提交大量抢票
业务防刷	绕过正常业务规则	多次占票但始终不支付
风险识别	识别异常行为组合	多账号集中参与抢票
风险处置	根据风险程度采取措施	限速、挑战验证、临时限制
资源保护	防止下游被流量打垮	MySQL 连接池耗尽
风险审计	记录判断依据和人工处理	误封申诉、规则调优
OWASP 的自动化威胁分类包括撞库、抢购囤票、虚假账号注册、库存占用攻击等，与票务平台的业务特征高度相关。

三、风险识别维度
建议第一版采用五个维度。

用户维度
登录失败次数、请求频率、重复抢票、反复取消订单、优惠券领取频率。




IP 维度
同 IP 请求速率、短期登录失败总量、短期注册数量、异常访问路径。




业务资源维度
演出活动、票档、领券模板的瞬时请求量、有效排队规模、库存占用。




设备 / 会话维度
登录会话、设备类型、短时会话切换；P1 才研究更复杂的设备识别。




系统容量维度
MySQL 活跃连接、MQ 积压、订单消费耗时、线程池队列和服务错误率。



不建议将共享 IP、使用代理、设备变化等单一信号直接等同于恶意用户。家庭、校园和公司网络都可能存在多人共享出口 IP 的情况。
四、多级限流方案
这是本模块最核心的技术能力。
我们之前已经确定采用 Redis Lua。这里把算法和业务场景进一步统一。
业务接口	建议算法	限流维度
登录	滑动窗口计数	账号、IP
注册	滑动窗口	IP、邮箱
邮箱验证码	固定冷却 + 滑动窗口	邮箱、IP
活动查询	令牌桶	IP、用户
抢票	滑动窗口 + 全局准入	用户、票档
抢券	滑动窗口 + 全局准入	用户、模板
支付尝试	滑动窗口	用户、订单
后台管理	权限检查 + 限流	管理员、接口
Redis 官方文档介绍了固定窗口、滑动窗口和令牌桶等算法。其中滑动窗口适合平滑限制请求数量，令牌桶允许受控突发流量。

幂等重试不能和新的业务请求完全混为一谈。
例如同一个 requestId 因网络超时再次提交，应优先安全查询原请求，而不是重复消耗一份抢票资格。
对于登录保护，也要避免攻击者故意输错密码导致正常用户长期无法登录。OWASP 建议结合多维限流、挑战和渐进式处置，而不是只依赖永久封锁账号。

五、风险决策与处置模型
建议第一版支持四种决策。
决策	含义	常见场景
ALLOW	允许进入后续业务	正常请求
THROTTLE	超过请求频率	接口高频访问
CHALLENGE	要求额外身份验证	可疑登录、异常抢券
DENY	拒绝业务请求	明确禁止的操作或严重异常
另外使用独立的临时限制记录控制某账号在一段时间内不能参与抢票或领券。
不建议把所有可疑请求都直接禁用整个账号。账号禁用应保留给用户与账号管理模块中的管理员或明确的高风险处置流程。
风险评分规则
为了让项目能够展示更丰富的工程设计，P1 可以增加简化的规则评分模型。
例如：

风控规则执行原则
1. 明确的黑名单、账号状态限制优先于普通评分规则。
2. 对高置信度的恶意请求可直接拒绝。
3. 中等风险优先采用限速或挑战，减少误伤。
4. 所有风险决策携带规则版本和风险原因码。
5. 管理员可启停规则，但不得静默修改历史决策记录。
6. 生产规则调整需要审计，重要规则应提供模拟评估与回滚能力。
六、抢票防刷专项设计
高并发票务系统最典型的滥用行为，不只是重复点击抢票。
还包括恶意占用有限库存，却长期不完成支付。
抢票风险场景
风险行为	识别信号	处理策略
高频抢票	同账号短时间大量新请求	用户级限流
重复请求	相同 requestId 重复提交	幂等返回，不重复处理
多笔占票	同账号同票档存在多个有效预占	原子限购与有效请求限制
长期不支付	一段时间内多次超时关闭	动态降低新抢票频率
多账号集中抢票	关联信号异常	P1 观察或挑战
绕过前台直接请求 API	非法参数、无有效认证	服务端鉴权和参数验证
销售暂停后继续抢票	命中旧销售配置	版本校验并拒绝
占票不支付如何处理？
例如一个账号连续 10 次抢到热门门票，又全部等到 15 分钟自动取消。
这种行为不一定证明账号恶意，但确实会影响其他用户购票。
建议设置滚动窗口内的超时未支付次数：
- 第一次、第二次：正常记录。
- 多次出现：降低该账号的抢票请求速率。
- 持续异常：短时间限制参与同一热门活动。
- 限制到期自动解除，并提供查询限制原因的渠道。
具体次数和时间窗口应通过压测及误伤分析调整，不建议一开始就设置永久封禁。
风控与库存一致性
风控只能阻止新的抢票请求。
对于已经创建的订单，不能因为用户后来被判定为高风险，就直接删除库存预占或把订单改成关闭。
如确需取消可疑订单，必须交给订单模块依据明确规则进行状态转换、释放库存并保留审计记录。
七、抢券防刷专项设计
营销模块已经设计了 Redis Lua 抢券及 MySQL 发行账本。
风控中心只负责外围保护，不重复实现领券额度扣减。
控制	风控中心	营销中心
用户请求限速	✓	—
IP 请求限速	✓	—
活动全局准入	✓	—
每人限领数量	—	✓
优惠券发行总量	—	✓
领券 requestId 幂等	—	✓
异常账号临时限制	✓	检查限制结果
优惠券生成和恢复	—	✓
必须注意：即使风控系统出现故障，营销模块仍然要保证模板不超发、用户不会绕过限领。

八、系统过载保护与降级策略
这一部分非常值得在大厂 Java 面试中重点介绍。
高并发系统不仅要防恶意请求，还要在正常用户集中抢票时保护数据库和消息队列。
8.1 四级保护架构
HTTP 请求入口
身份校验、参数校验、基础请求限流


Redis Lua 风控准入
用户、IP、票档、营销活动多维限流


抢票 / 领券请求受理
持久化请求、控制待处理规模


RocketMQ 有界消费
消费并发、积压、等待时间监控


MySQL 交易事务
最终库存、限购、订单和支付约束


8.2 系统保护状态
建议为热门票档的准入控制设置独立状态。
状态	含义	新抢票请求
NORMAL	正常容量	正常受理
THROTTLED	资源接近上限	降低受理速率
PAUSED	暂停新受理	拒绝新请求
RECOVERING	正在恢复或重建	暂停或严格限制受理
这些是系统准入保护状态，不属于演出、订单或库存的业务状态机。
即使暂停新抢票，也必须尽可能继续处理已经可靠受理的订单、支付确认、关单和库存补偿。
8.3 根据哪些指标触发降级？
指标	推荐动作
MySQL 连接池等待显著增加	降低新请求准入速率
RocketMQ 待处理请求持续增长	减少入口受理量
最早排队请求等待时间过长	停止受理无法及时处理的新请求
库存对账出现严重差异	暂停受影响票档
Redis 库存状态不可信	暂停对应业务入口并重建
应用错误率持续升高	进入保护状态并告警
这里不设置统一的固定 CPU 或 MQ 积压阈值。应先通过压测测量系统稳定吞吐量，再按实际容量配置。
8.4 Redis 故障时怎么办？
需要按接口重要性区别处理。
接口类型	Redis 不可用时
公开活动查询	可以有限度使用本地缓存，必要时限速
普通资料查询	保持认证安全前提下继续服务
登录与 Token 刷新	无法安全验证会话时拒绝
抢票	暂停新的高并发准入
领券	暂停新的高并发发行
已受理的交易恢复	根据 MySQL 权威状态继续可安全执行的恢复
订单支付和取消	不盲目拒绝；满足会话安全及交易状态要求时按数据库事务处理
不能采用“一旦 Redis 宕机，所有接口直接不检查限流和身份状态”的策略。
九、Redis Key 规划
沿用之前确定的 Redis 7.4 + Lettuce + Lua。
Redis Key	数据类型	作用
ft:risk:rate:user:{userId}:{api}	Hash	用户接口令牌桶
ft:risk:rate:ip:{ipHash}:{api}	Hash	IP 维度限流
ft:risk:rate:event:{eventId}	Hash	活动准入限流
ft:risk:rate:coupon:{templateId}	Hash	抢券准入限流
ft:risk:login:fail:{accountHash}	String	登录失败次数
ft:risk:login:lock:{accountHash}	String	临时登录保护
ft:risk:restriction:user:{userId}	Hash	用户业务临时限制
ft:risk:restriction:ip:{ipHash}	Hash	IP 临时限制
ft:risk:admission:{tierId}	Hash	票档准入状态与规则版本
ft:risk:rule:version	String	风控规则缓存版本
Redis 使用原则
- Redis Lua 原子完成令牌补充、检查和消费。
- 使用 Redis 服务端时间或其他统一可信时间来源，减少多应用实例时钟偏差。
- 计数器设定合理 TTL，防止长期占用内存。
- 全局限流和用户限流分开实现，不能只限制单个用户。
- 对同一个用户和多种资源的检查，需要明确部分检查通过、后续检查失败时是否消耗令牌。
- Redis 中的黑名单和临时限制需要与 MySQL 持久化规则协调，不能让 Redis 数据丢失导致管理限制永久消失。
如果使用 Redis Cluster，涉及同一个 Lua 脚本的 Key 应设计相同 Hash Slot；不同维度的 Key 不必强行全部放入一个大脚本。
十、业务风险规则与处置状态
建议区分三类记录：
1. 风险规则：定义什么行为需要处理。
2. 风险事件：记录发生了什么可疑行为。
3. 风险限制：记录已经对谁采取了什么限制。
风险限制状态机
ACTIVE · 限制生效


EXPIRED
到期自动解除


REVOKED
管理员提前解除




临时限制还应记录限制的业务范围，例如：
- 只限制登录尝试。
- 只限制某个票档抢票。
- 只限制某个营销活动领券。
- 限制全部新抢票请求。
不要把业务限制直接等同于用户账号 DISABLED。
十一、数据库实体规划
第一版建议设计六张核心风控表。
表名	职责	关键字段
ft_risk_rule	风控规则定义	rule_id、scene、action、priority、version
ft_risk_rule_version	规则版本快照	rule_id、version、configuration
ft_risk_event	风险行为记录	event_id、user_id、scene、risk_code、occurred_at
ft_risk_decision	风险决策记录	decision_id、request_id、action、matched_rules
ft_risk_restriction	黑名单及临时限制	subject_type、subject_id、scope、expire_at、status
ft_risk_operation	管理员操作审计	operator_id、target_id、action、reason
P1 可扩展 ft_risk_appeal，记录用户申诉和人工复核。
数据保存原则
风控事件可能非常多，不建议所有正常请求都同步插入 MySQL 风险日志表。
第一版可以采用：
- 正常放行请求：聚合指标为主。
- 限流命中：短期计数与采样记录。
- 高风险拒绝：保存关键决策记录。
- 管理员限制和解除：保留可审计的持久化记录。
- 安全日志：设置合理保留周期、访问权限和脱敏规则。
大量低价值风控事件不应拖慢抢票核心事务。
十二、RocketMQ 消息设计
风控模块可以使用 RocketMQ 进行异步风险事件处理，但不应让需要实时执行的准入决策依赖 MQ 消费完成。
消息事件	Topic	用途
RISK_DETECTED	ft-risk-event	异步记录风险事件
RISK_RESTRICTION_CREATED	ft-risk-event	限制生效通知
RISK_RESTRICTION_REVOKED	ft-risk-event	限制解除通知
RISK_ALERT_TRIGGERED	ft-risk-event	通知管理员
RISK_RULE_UPDATED	ft-risk-event	规则变更通知
采用 Normal 消息，消费端幂等。
对于管理员创建黑名单这种关键变更，应先在 MySQL 事务中可靠持久化，再使用 Outbox 发布更新事件。
RocketMQ 主要用于审计、通知及非实时统计。

十七、风险控制与防刷模块 V1.0 定稿
FlashTicket 风控业务方案


技术架构： Spring Boot 单体风控模块 + Redis Lua + MySQL + RocketMQ。
保护对象： 登录、注册、验证码、活动查询、抢票、领券、支付及管理端接口。
限流模型： 用户、IP、活动、票档、优惠券模板多维度限流，滑动窗口和令牌桶相结合。
风险决策： ALLOW / THROTTLE / CHALLENGE / DENY。
风险处置： 临时限制优先，不轻易永久禁用账号；支持管理员解除与审计。
系统降级： 根据 MQ 积压、数据库资源和 Redis 状态控制新请求准入。
可靠性： 风控结果不能替代业务幂等、库存原子扣减和数据库事务。
面试重点： Redis Lua、限流算法、多维限流、热点治理、背压、熔断降级、故障恢复和防止误伤。
