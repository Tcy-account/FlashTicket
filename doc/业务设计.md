FlashTicket 业务设计 · 第一步：用户角色与权限体系
现在进入 FlashTicket 的业务需求设计阶段。首先确定系统有哪些用户、每种用户能做什么，以及权限如何划分。
结合我们已经确定的 Spring Security 6 + JWT + Redis + RBAC，我建议采用：
两类用户入口、五种系统角色、基于 RBAC 的功能权限管理，并结合数据归属校验。

五种角色的职责
角色	业务职责	使用端
USER 普通用户	查看演出、抢票、支付、退款申请、查看自己的订单	用户端
OPERATOR 运营人员	发布活动、管理场次、票档、销售规则	管理端
FINANCE 财务人员	查看支付记录、模拟退款审核、对账	管理端
ADMIN 系统管理员	管理后台账号、角色、权限和系统参数	管理端
SUPER_ADMIN 超级管理员	全部后台权限、初始化权限配置	管理端
另外有一种 游客（Guest），它不是数据库角色，而是未登录的访问状态。游客可以浏览公开演出，但不能抢票、支付或者查看个人订单。

三、RBAC 权限模型
建议使用 RBAC0（用户—角色—权限）+ 资源归属检查，第一版不引入复杂的角色继承体系。

USER / OPERATOR / FINANCE / ADMIN / SUPER_ADMIN

运维	inventory:reconcile	处理库存对账异常
普通用户自己的订单、支付、退款申请属于身份认证 + 资源归属授权，不必为每个操作都创建独立的后台 RBAC 权限。
例如，用户 A 访问用户 B 的订单，即使 A 已登录，也必须拒绝。
四、用户账户和后台账户是否分开？
这里建议你采用 统一账号体系、区分登录入口。
也就是：
- 用户端：普通用户登录。
- 管理端：具备后台角色的账号才能登录。
- 数据库：共享用户主体与用户角色关联。
- Token：携带必要的身份与会话标识，后台访问需要服务端验证后台角色。
- 账号：一个用户可拥有多个角色，但普通注册用户不能自行申请或修改为管理员。
这样可以避免维护两套重复的登录、密码、Token、用户状态和安全策略。
管理端账户建议由管理员创建，不开放公开注册。敏感权限变更还需要审计日志。
五、运营管理人员的数据范围
虽然我们采用模块化单体，但可以提前为权限设计一个简单的数据范围模型。
数据范围	含义	应用示例
OWN	只管理自己创建或负责的活动	普通运营人员
ALL	管理全平台活动	高权限运营主管
ASSIGNED	管理明确分配的活动	指定演出负责人
这三种数据范围可以作为后续 P1 功能，第一版建议先让运营人员管理全平台的非敏感活动业务，再逐步加入活动归属和负责人分配。
需要特别注意：数据范围应作为查询条件和写操作授权条件实施，而不是只在前端隐藏按钮。
六、第一版建议实际实现哪些角色？
为了减少开发工作量，建议五个角色都在数据库中预置，但分阶段完善功能。
P0
USER、OPERATOR、SUPER_ADMIN
先完成购票、活动运营和最高权限管理，确保核心交易链路可以运行。



P1
FINANCE、ADMIN
完善退款审核、财务统计、后台账号和角色管理。



七、用户角色方案定稿
我建议直接确定：
FlashTicket 用户角色 V1.0：
- 访客 Guest（未登录状态）
- 普通用户 USER
- 运营人员 OPERATOR
- 财务人员 FINANCE
- 系统管理员 ADMIN
- 超级管理员 SUPER_ADMIN
统一用户主体、RBAC0 权限模型、后台独立登录入口、资源归属校验，后续支持数据范围 OWN / ASSIGNED / ALL。
这样既覆盖普通购票业务，也覆盖管理端的运营、财务和权限控制，符合 Java 后端实习项目需要展示的鉴权和业务建模能力。
