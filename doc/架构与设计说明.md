# FlashTicket 架构与设计说明

面向评审的一页架构说明。事实来自仓库包结构、`README.md`、`doc/M17-05-架构图.md` 与对应 Java 实现。范围是**演出抢票与票务订单后端**（数量型票档、模拟支付），不是完整电商商城，也不是微服务。

## 1. 形态：模块化单体

单 Maven 工程 `backend/`，Spring Boot 3.5 / Java 21。领域代码在 `backend/src/main/java/com/flashticket/`，按包划边界，进程内调用，共享一个 MySQL。

跨域只允许「编排服务 → 领域服务」。业务包禁止跨域直接调用对方 Mapper（README 工程约定）。

| 层 | 包 | 职责 |
|---|---|---|
| 编排 | `purchase` `payment` `refund` | 抢票受理、支付确认、退款，跨库存/订单/权益 |
| 领域 | `identity` `event` `inventory` `order` `entitlement` `coupon` `risk` `notification` `analytics` `reconciliation` | 账号、演出、库存账本、订单状态机、门票、券、限流、通知、统计、对账 |
| 基础设施 | `messaging` `common` `system` | Outbox/Inbox、响应信封与 JWT、健康检查 |

表前缀 `ft_`。Flyway 在 `backend/src/main/resources/db/migration/`，`V1__baseline_init.sql` 到 `V17__reconciliation.sql`。雪花主键在 API 里用字符串，金额是 BIGINT 分，时间 `DATETIME(3)` UTC。

统一前缀 `/api/v1`，信封 `{code, message, data, requestId, traceId, timestamp}`。HTTP 状态表示传输结果，`code` 表示业务结果。

## 2. 异步抢票

同步建单会把库存扣减堵在 HTTP 线程上。当前路径是受理与建单拆开（`purchase` + `messaging`）：

```text
POST /api/v1/purchases
  → PurchaseController 返回 HTTP 202
  → PurchaseCheckoutService.accept（同一 MySQL 事务）
       ft_purchase_request = QUEUED
       ft_outbox_event     = PENDING（topic 默认 ft-purchase）
  → OutboxPublisher 约 1s 扫描，领发布租约后经 RocketMQPublisher 发到 proxy gRPC :8081
  → PurchaseRequestListener（消费组 ft-purchase-cg）
  → PurchaseRequestProcessor
       Inbox 查重 → 领处理租约 QUEUED/RECOVERING→PROCESSING
       → PurchaseOrderBuilder（同一事务）
            InventoryService.reserve
            OrderService.createOrder（PENDING_PAYMENT）
            请求 SUCCEEDED + 写入 ft_message_inbox
  → RocketMQOrderCloseDelaySender 发 ft-order-close 延迟消息（失败则靠 DB 扫描）
```

受理成功只表示已排队。`CheckoutResponse.status` 为 `QUEUED` 时 `order` 为 null。轮询 `GET /api/v1/purchases/{requestId}`，只有 `SUCCEEDED` 才有订单。

受理前的快速拒绝（不代替库存账本）：

- `RateLimitService.checkPurchase`：默认同账号同票档 5 秒 1 次（`application.yml`）
- `RiskRestrictionService`：临时限制
- `PurchaseEligibilityService`：场次/票档/开售窗口
- `InventoryAdmissionService.tryAdmit`：Redis 准入。默认 `flashticket.inventory.redis-admission.enabled=false`（模式 2，MySQL 权威）。打开后是模式 3：快照不足则入口拒绝；快照缺失或 Redis 异常回退 MySQL，不阻断受理

权威扣减发生在消费端 `InventoryService.reserve`，见 `doc/深挖-条件扣减防超卖.md`。

## 3. 库存预占与确认

`inventory.InventoryService` 维护三态账本（`ft_inventory`，主键即 `tier_id`）：

```text
total = available + reserved + sold
```

`V7__inventory_reservation_ledger_limit.sql` 用 `chk_inv_conservation` 做 CHECK。变更只走 `InventoryMapper` 手写条件 `UPDATE`，看受影响行数，不用 MyBatis-Plus `@Version`。

| 动作 | 时机 | 账本 | 预占状态 |
|---|---|---|---|
| INIT | 票档发布 `initialize` | total = available | — |
| RESERVE | 消费端建单 | available -= q，reserved += q | RESERVED |
| CONFIRM | 模拟支付成功 | reserved -= q，sold += q | CONFIRMED |
| RELEASE | 用户取消或超时关单 | reserved -= q，available += q | RELEASED |

预占以 `request_id` 幂等。确认与释放只允许从 `RESERVED` 转出，重复调用按终态返回。流水在 `ft_inventory_ledger`（`INIT/RESERVE/CONFIRM/RELEASE`）。限购在 `ft_purchase_limit`，占用时 `SELECT … FOR UPDATE`。

## 4. 支付与关单竞争

模拟渠道 `MOCK_WALLET`（`PaymentService`），不接真实支付网关。

支付确认与关单抢的是同一行订单，且都只在 `PENDING_PAYMENT` 上更新：

- 支付：`OrderService.markPaid` → `OrderMapper.paidById`，`WHERE status='PENDING_PAYMENT' AND expire_at > now` → `PAID`
- 关单：`OrderMapper.closeById`，`WHERE status='PENDING_PAYMENT'` → `CLOSED`

受影响行数为 1 的一方继续后续动作；为 0 则重查终态。因此不会同时变成 `PAID` 和 `CLOSED`。

关单有两条触发，最终都进 `OrderCloseService.doClose`（释放预占、返券、写 `ft_order_operation`）：

1. 建单成功后的延迟消息：`ft-order-close` / tag `ORDER_CLOSE`，`OrderTimeoutDelayConsumer`。发送失败只打日志。
2. 数据库兜底：`OrderTimeoutScheduler` 默认约 30 秒扫一次 `expire_at` 已到且仍为 `PENDING_PAYMENT` 的订单。支付期限默认 15 分钟（`flashticket.order.payment-timeout-minutes`）。

支付幂等键是 `ft_payment_attempt.attempt_request_id`（唯一索引 `uk_attempt_request`）。细节见 `doc/深挖-支付幂等与关单补偿.md`。

## 5. 可靠性要点

- **受理不丢**：请求与 Outbox 同一事务。MQ 停机时 Outbox 停在 `PENDING`，恢复后 `OutboxPublisher` 补发。`doc/M17-03-故障演练复盘.md` 记录了一次 broker/proxy 停止后的补发。
- **消费不重**：`ft_message_inbox` 唯一键 `(consumer_name, event_id)`；建单成功路径在 `PurchaseOrderBuilder` 里与订单同事务插入。处理租约在 `PurchaseRequestMapper.acquireLease`（`lease_owner` / `lease_until`，默认 30 秒）。
- **崩溃恢复**：`PurchaseRecoveryScanner` 扫三类：租约过期的 `PROCESSING`、到点的 `RECOVERING`、超过 `accepted_deadline_at` 的 `QUEUED`（失败原因 `QUEUE_TIMEOUT`）。补发新 `eventId`、沿用原 `requestId`。
- **发布不重**：`OutboxEventMapper.acquireLease` / `markSent` 要求仍持有 `lease_owner`。

## 6. 监控

- 存活：`GET /api/v1/health` → `data.status=UP`（`system.health.HealthController`）
- 就绪：`GET /api/v1/health/readiness`，`SELECT 1` + Redis `PING`。任一失败 HTTP 503，业务码 `SERVICE_UNAVAILABLE`
- 指标：Actuator 暴露 `health,info,metrics,prometheus`（`micrometer-registry-prometheus`）。本地 Prometheus 抓 `host.docker.internal:8080/actuator/prometheus`（`docker/prometheus/prometheus.yml`）
- Grafana：`http://localhost:3000`，账号 `admin/admin`，看板标题「FlashTicket 运营监控」（JVM 堆、HTTP 速率、CPU、抢票接口 QPS 面板）。生产 profile 不把 prometheus 暴露到公网（`application-prod.yml` 只留 `health,info`）

代码里没有手写业务 Counter；看板上的 QPS 来自 Actuator HTTP 指标，不是单独埋点的业务吞吐。
