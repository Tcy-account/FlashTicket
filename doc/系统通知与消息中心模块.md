FlashTicket 业务需求设计 09：系统通知与消息中心模块
推荐方案 V1.0
Notification & Message Center · 业务与架构设计

本模块负责 FlashTicket 平台的站内消息、抢票结果通知、订单支付提醒、退款进度通知、系统公告、实时消息推送、已读管理及消息可靠投递。
它既是用户体验模块，也是展示 RocketMQ 异步解耦、MySQL 事务、Redis 缓存、SSE 长连接和消息幂等能力的重要部分。
本轮继续只做业务需求与架构设计，不编写代码或数据库 DDL。
一、核心设计目标
通知中心必须解决六个问题：
1. 用户抢票成功或失败后，能够及时知道结果。
2. 用户不在线时，重要通知不会因 SSE 断开而消失。
3. RocketMQ 重复投递时，不会产生多条重复通知。
4. 通知发送失败能够重试，但不影响已经完成的支付或订单事务。
5. 普通用户只能看到自己的消息，管理员能够管理公告和通知模板。
6. 高并发抢票时，不会因为大量通知推送拖垮核心交易服务。
需要先区分三个概念
概念	作用	是否要求持久化
业务事件 Business Event	记录订单创建、支付成功、退款成功等业务事实	关键事件必须可靠
站内通知 Notification	用户可以在消息中心查看的消息	是
实时推送 Push	将新的状态或消息及时送到在线客户端	不单独要求可靠，但必须可恢复查询
RocketMQ 是异步事件传输组件，MySQL 是通知记录的事实来源，SSE 负责在线实时体验。
不能把“RocketMQ 发送成功”或者“SSE 推送成功”直接等同于“用户已经阅读消息”。

三、通知类型设计
推荐将通知分成四类。

交易通知 TRANSACTION
抢票结果、订单创建、支付成功、订单关闭、退款完成。重要程度最高。




演出通知 EVENT
演出延期、取消、场馆变更、购票场次变化。




营销通知 MARKETING
优惠券发放、领券失败、优惠券临期提示、营销活动通知。




系统通知 SYSTEM
账号安全提醒、系统维护公告、重要平台通知。

核心事务边界
通知消费端应在一个 MySQL 本地事务中完成消费去重与站内消息创建。
如果数据库事务提交成功但 MQ 的消费确认失败，消息可能被再次投递；通过 eventId + notificationType + receiverId 等稳定唯一键保证不会重复生成。
通知创建成功后才进行实时推送。 SSE 推送失败不能回滚已创建的通知，也不应该使已经成功完成的订单或支付重新执行。
五、通知生命周期与已读管理
建议将通知生成状态、推送状态、阅读状态分开设计。
5.1 用户站内消息状态
对于站内消息，第一版只需管理：
- UNREAD：未读。
- READ：已读。
消息生成后默认为未读。用户点击消息或执行“标记已读”后转成已读，不允许普通用户重新设为未读。
另外提供用户侧软删除或隐藏（P1），但删除可见消息不能影响原始业务事件和财务审计记录。
5.2 实时推送状态
SSE 不需要复杂的永久投递状态机，可将推送看作最佳努力的在线事件。
站内通知已持久化

SSE 推送成功不代表浏览器已经显示消息，更不代表用户已经阅读。因此未读数只由持久化的用户阅读状态决定。
六、SSE 实时推送方案
此前抢票模块已经确定使用 SSE。这里我建议统一实时推送基础设施，避免抢票模块和消息模块各维护一套完全独立的连接管理器。
两类实时事件
事件类型	说明	是否创建站内通知
purchase.queued	抢票请求排队	否
purchase.processing	正在处理	否
purchase.succeeded	抢票成功	是
purchase.failed	抢票失败	是
notification.created	新站内消息	已存在
notification.unread-count	未读数更新提示	否
order.status-changed	订单状态变化	按事件规则决定
建议采用统一用户 SSE 通道
GET /api/v1/notifications/stream
建立连接后只推送当前登录用户有权接收的消息。
抢票详情页可以保留 /api/v1/purchases/{requestId}/events，但与通知流共享底层 SSE 连接管理、心跳和鉴权组件；第一版也可以只使用统一通道加 HTTP 状态查询，减少浏览器长连接数量。
SSE 连接管理要求
项目	推荐规则
连接身份	已登录用户 + 当前会话
连接数量	每个有效会话最多一个主消息连接
心跳	建议每 15–30 秒
断线恢复	重新连接后 REST 补查
数据授权	仅推送本人消息
连接过期	需要重新验证认证信息
旧连接清理	断开、超时或会话撤销后移除
多设备登录	每个有效会话可接收本人的实时提示
由于原生浏览器 EventSource 不支持任意自定义 Authorization 请求头，实际开发时应为 SSE 设计安全的同站点 Cookie 认证或短期专用连接凭证。不能把长期 JWT 放进 URL。
多实例扩展
第一版虽然采用模块化单体，但以后可以同时运行多个相同的 Spring Boot 实例。
若用户连接在实例 A，而 RocketMQ 消费者在实例 B，B 无法直接访问 A 内存里的 SSE 连接。
因此建议后续使用 Redis Pub/Sub 做跨实例实时事件分发，所有实例仅向本地连接的对应用户推送。
但 Redis Pub/Sub 是即时通知机制，不承担可靠事件存储；Redis 消息丢失时，仍然通过 MySQL 通知记录和 REST 补查恢复。
七、站内消息的数据模型
建议采用通知内容与用户接收记录分离的结构，既支持个人通知，也方便以后发布全平台公告。
表名	职责	关键字段
ft_notification	通知内容与业务关联	id、type、title、content、biz_type、biz_id、event_id
ft_notification_recipient	接收人及阅读状态	notification_id、user_id、read_at、hidden_at
ft_notification_template	可配置通知模板	code、title_template、content_template、version、status
ft_notification_delivery	外部渠道发送记录（P2）	notification_id、channel、status、attempt_count
ft_announcement	系统公告（P1）	title、content、publish_at、expire_at、status
其中 P0 核心表只有前两张，模板可以先采用服务端固定定义，等 P1 再做管理界面。
核心数据库约束
- 同一业务事件、通知类型与接收人不能重复生成通知。
- 一个接收人对一条通知只能有一条接收记录。
- read_at 初始为空，阅读后记录首次已读时间。
- 用户不能更新其他用户的阅读状态。
- 通知内容需要保存业务发生时必要的快照，避免订单名称或活动标题后续修改导致历史消息意义改变。
- 业务跳转目标必须由服务端确定，不能存储未经校验的任意外部跳转 URL。
- 个人敏感信息不应放入所有用户共享的通知正文。
为什么内容和接收人分开？
例如演出取消，需要通知 10,000 名购票用户。
如果为每个人创建一条完全相同的公告内容，会产生大量重复存储。
可以只创建一份通知内容，再为每个用户创建独立的接收关系和已读状态。
不过这不意味着可以一次性在大事务中插入 10,000 条接收记录。应按照受众快照和可恢复的批次分发，控制数据库事务规模。

十、系统公告与批量通知
系统公告属于 P1，但建议现在预留设计。
公告范围	示例
全平台用户	平台维护公告
指定演出用户	演出延期或取消
指定场次用户	场次入场时间变更
指定票档用户	票档相关说明
管理员	系统风险告警
批量通知的可靠性要求
例如某场演出取消，需要通知所有已支付购票用户：
1. 在数据库中持久化公告或通知任务。
2. 根据有效订单确定受众，并保存受众快照或可恢复的遍历边界。
3. 分批创建接收人记录，每批独立事务提交。
4. 记录处理游标和失败信息，避免中途崩溃后从头重复生成。
5. 对在线用户发送 SSE 提示。
6. 离线用户登录后通过消息中心读取。
系统公告不能只依赖一次 Redis Pub/Sub 广播，因为离线用户会漏掉消息。
十一、RocketMQ 消息可靠性
继续沿用第五步已经确定的 RocketMQ 方案：
RocketMQ 5.x + PushConsumer + Transactional Outbox + Inbox 幂等 + 自动重试 + DLQ。
消息资源规划
Topic	类型	Consumer Group	职责
ft-notification	Normal	ft-notification-cg	根据业务事件创建站内通知
ft-announcement	Normal	ft-announcement-cg	批量公告受众处理（P1）
不建议为了每一种通知单独创建一个 Topic。通知的业务类型可以放在消息体的 eventType 和 notificationType 中。
通知创建消费规则
- 先检查消息消费记录与通知业务唯一键。
- 创建通知内容、接收记录和消费完成标识。
- 在一个本地事务中提交。
- 成功后确认消费。
- 若消费失败，按可重试异常和确定性错误分类处理。
- 超过重试次数时，进入死信处理，并由后台提供异常恢复能力。
RocketMQ 消费失败和重试可能导致重复投递，使用 Inbox 和业务唯一约束进行防重是必要的。
不同失败的处理
异常	处理策略
MySQL 暂时不可用	MQ 重新投递
通知已经存在	幂等视为成功
模板参数无效	记录永久失败，进入异常处理，不无限重试
用户账号已注销	按数据保留政策处理，不盲目创建消息
SSE 推送失败	不重试业务消费，等待用户 REST 补查
消息格式版本不兼容	隔离异常事件，告警处理
Broker 不可用	Outbox 保留未发布事件并重试
注意：SSE 的推送异常不能让已经成功创建的通知消息反复进入 RocketMQ 消费重试。
十二、Redis 设计
Redis 在本模块只用于提升实时体验与读取性能，不承担通知最终持久化。
Redis Key	类型	用途
ft:notification:unread:{userId}	String	用户未读数量缓存
ft:notification:stream:{sessionId}	Hash / 连接管理辅助状态	SSE 会话元数据（按需）
ft:notification:rate:{userId}	String	用户通知推送频率控制
ft:notification:announcement:{id}	String	公告展示缓存
ft:notification:template:{code}	String	通知模板缓存
未读数在 MySQL 中可以通过接收记录统计，Redis 仅作缓存。
如果未读数缓存失效或计数异常，应重新查询持久化数据并修正缓存，而不是把 Redis 数值当成唯一真相。
SSE 的实际连接对象必须保存在对应 Spring Boot 实例的内存中，不能将 Java 连接对象序列化保存到 Redis。

十七、系统通知与消息中心模块 V1.0 定稿
FlashTicket 通知业务方案


通知渠道： V1 实现站内消息 + SSE，外部邮箱、短信后续扩展。
消息类型： 交易通知、演出变更、营销通知、系统公告。
数据模型： 通知内容与用户接收记录分离，独立保存已读状态。
事件可靠性： 业务事务 + Outbox → RocketMQ → Inbox 幂等 → MySQL 通知持久化。
实时推送： SSE 只负责在线通知，断线后通过 REST 补查。
多设备： 用户消息和未读状态共享，SSE 按会话维护连接。
多实例： P1 使用 Redis Pub/Sub 分发在线事件，数据库仍是通知事实来源。
批量通知： 分批发放、进度持久化、失败恢复，不在核心订单事务中批量生成通知。
面试技术重点： RocketMQ 可靠消费、Outbox、幂等、SSE 长连接、Redis 缓存一致性、批量处理与背压。
