FlashTicket 业务需求设计 05：订单与交易状态机模块
Order & Transaction Lifecycle · V1.0 · Java 模块化单体
订单中心是连接抢票、库存、模拟支付、退款和用户购票记录的核心业务模块。
前面的模块已经确定了抢票请求如何可靠受理、如何通过 RocketMQ 异步处理，以及如何预占库存。现在需要解决：抢到票以后，如何安全地创建订单、保持门票、完成支付、取消订单和超时关单。
本轮继续只做业务需求与架构设计，不编写 Java 代码或数据库 DDL。
一、订单模块的设计目标
我们把订单模块的核心能力分为五项：
创建订单
抢票成功后生成唯一订单


订单状态机
控制合法的状态转换


取消与关单
释放未支付订单的预占库存


交易快照
保留成交时的票价与演出信息


订单查询与审计
支持历史追踪、查询与故障恢复



核心设计原则：
1. 一个抢票请求最多生成一个有效订单。
2. 一个订单只能有一个合法的最终支付或关单结果。
3. 库存预占、订单创建和请求成功状态应在同一个 MySQL 本地事务中提交。
4. 支付、取消、超时关单不能各自随意修改库存，必须经过订单状态机协调。
5. RocketMQ 可以重复投递，但不能导致重复创建、重复释放和重复交易。
6. 历史订单必须保留购票时的价格、场次和票档快照，不受后续修改影响。
二、订单模块与其他模块的职责边界
模块	职责
抢票模块 purchase	请求受理、排队、限购校验、抢票结果
库存模块 inventory	预占、确认已售、释放、库存流水
订单模块 order	创建订单、状态流转、取消、超时、订单查询
支付模块 payment	发起支付、模拟回调、支付流水
退款模块 refund	退款申请、审核、模拟原路退款
消息模块 messaging	Outbox 发布、Inbox 幂等、消息消费
通知模块 notification	订单创建、支付成功、退款结果通知
特别注意： 支付模块不能绕过订单模块直接将订单状态设为 PAID；订单模块也不能伪造支付渠道的成功结果。两者通过同一个单体应用中的交易编排服务进行协调。
三、订单业务规则
3.1 订单基本类型
第一版只支持一种订单：
普通演出票购买订单（TICKET_ORDER）。
建议规则如下：
项目	V1.0 规则
订单类型	普通演出票
购买方式	高并发抢票
每笔订单	一个场次、一个票档
购买数量	1–2 张，可按票档限购配置
库存占用	创建订单时完成数据库预占
支付期限	15 分钟
订单金额	购买时票价 × 数量
货币	CNY，金额使用整数分
优惠券	V1 暂不启用，P1 扩展
支付方式	模拟支付
真实出票与核验	P1 扩展，当前以已支付订单作为购票凭证
不建议第一版支持跨场次购物车或一笔订单包含多个票档。这会立刻引入多库存行加锁、部分预占失败回滚及复杂拆单问题，不利于把高并发主线先做扎实。
3.2 订单编号
继续沿用已经确定的三类标识：
ID	用途
orderId	内部雪花 BIGINT 主键
orderNo	用户可见的唯一业务订单号
requestId	抢票请求的全局幂等标识
requestId 和 orderNo 都必须有数据库唯一约束。不能因为客户端重试而创建不同订单号。
四、订单状态机
这里要做一个重要决定：
不把退款状态、消息发送状态、库存 Redis 预占状态全部塞进订单状态枚举。
第一版订单只管理交易生命周期。
PENDING_PAYMENT
待支付 · 门票已预占


PAID
支付已确认


CLOSED
取消或超时关闭




退款子流程
由独立退款状态控制，成功后可形成 REFUNDED 订单展示状态

退款仅从已支付订单发起；已关闭订单不能直接恢复待支付或变成已支付。退款流程不改变未支付关单规则。
状态转换表
原状态	业务事件	目标状态	库存变化
不存在	抢票成功创建订单	PENDING_PAYMENT	available → reserved
PENDING_PAYMENT	支付成功确认	PAID	reserved → sold
PENDING_PAYMENT	用户取消	CLOSED	reserved → available
PENDING_PAYMENT	支付超时关单	CLOSED	reserved → available
PAID	退款申请	仍为 PAID，退款流程独立	暂不改变
PAID	退款成功	形成 REFUNDED 展示终态	由退款规则决定
CLOSED	重复关单	CLOSED	不变
PAID	重复支付回调	PAID	不变
取消和超时都归入 CLOSED，另外用 closeReason 解释原因：
- USER_CANCEL
- PAYMENT_TIMEOUT
- EVENT_CANCELLED
- SYSTEM_CANCEL
这样查询和统计更清楚，也不需要为每一种关闭原因单独扩充订单主状态。
为什么不立即增加 PAYING 状态？
因为第一版模拟支付可以通过支付单状态表达支付处理中。
订单侧只需区分待支付、已支付、已关闭。但为了正确处理支付成功和超时关单的竞争，支付模块必须具备“支付受理中、成功、失败、过期或结果待确认”等状态，并有最终确认点。
后续接入真实支付渠道时，再根据异步支付的复杂度评估是否增加订单级 PAYMENT_CONFIRMING 等受控中间状态。
五、订单创建流程
订单不能由用户直接调用一个普通的创建接口来绕过抢票规则。
推荐由 RocketMQ 抢票消费者调用订单应用服务，在同一个 MySQL 事务中完成以下操作。
RocketMQ 抢票消息
requestId · userId · tierId · quantity


MySQL 本地事务
1. 检查请求幂等与消费处理资格
2. 原子占用用户票档限购额度
3. 调用库存模块确认预占
4. 创建订单和订单明细快照
5. 更新抢票请求为成功状态
6. 写入订单创建 Outbox 事件


事务提交
订单可查询，库存预占生效


发送后续业务事件
超时关单计划 · 用户结果通知


任何一步数据库操作失败，本地事务整体回滚。
对于此前 Redis Lua 已经发放的临时预占资格，则需要按照库存模块设计的恢复与补偿协议处理，因为 Redis 操作不能跟随 MySQL 本地事务自动回滚。
订单创建成功的判断标准
必须同时具备：
- 一条有效订单。
- 与订单关联的库存预占记录。
- 与订单对应的有效限购占用。
- 抢票请求被标记为 SUCCEEDED。
- 已持久化的后续业务事件。
不能出现“抢票状态成功，但订单不存在”这样的已提交业务状态。
六、订单支付期限和超时关单
确定订单有效期为 15 分钟。
这里有个细节：支付期限从订单在数据库中成功创建的时间开始计算，而不是从用户点击抢票或进入 RocketMQ 排队时开始。
例如：
请求提交
10:00:00


排队完成并创建订单
10:00:08


支付截止时间
10:15:08

示例时间，展示订单 15 分钟支付期限的计算方式。
时间的权威来源应统一，数据库存储 UTC 时间。前端倒计时只负责展示，服务端不能相信浏览器提交的剩余时间。
6.1 超时关单采用双重保障
第一层：RocketMQ 5.x Delay 消息。
订单创建后，通过可靠事件机制安排到期检查。RocketMQ 5 的定时/延迟消息支持指定投递时间，但并不意味着消息会在设定时刻精确完成业务处理。RocketMQ 官方延迟消息文档。
第二层：Spring Scheduling + MySQL 到期扫描。
即使 RocketMQ 延迟消息没能及时被处理，也能通过数据库扫描发现已经过期的订单。
扫描条件包括：
- 订单仍为 PENDING_PAYMENT。
- 订单的支付期限已经达到。
- 没有优先取得支付最终确认资格的事务或待决状态。
- 当前任务能够获得合法的订单处理权。
6.2 用户主动取消
只有待支付订单可以直接取消。
当前订单情况	处理
待支付且未进入最终支付确认	允许取消
正在确认支付结果	等待确认或返回处理中，不直接释放
已支付	不允许取消，需申请退款
已关闭	幂等返回已关闭
订单不存在	返回不存在或无访问权限
用户取消和系统超时都必须经过同一套订单关闭服务，避免两份逻辑分别修改库存。
七、最重要的并发问题：支付与关单竞争
这是整个订单模块最值得深入研究的技术问题。
假设订单只剩最后一秒：
- 用户发起支付。
- RocketMQ 同时触发超时关单。
- 两个处理线程几乎同时读到待支付状态。
如果只依赖先查询再更新，可能发生重复处理或非法状态覆盖。
正确性要求
支付成功和关闭订单必须争夺同一个受数据库保护的订单状态转换权。
MySQL InnoDB 对更新语句提供必要的行级锁机制，能够支持条件状态转换。

MySQL
+1



PENDING_PAYMENT


支付处理
确认有效支付结果，更新订单与库存


关单处理
核验到期条件，关闭并释放库存




只能提交一个合法结果
数据库状态约束 + 同一事务内修改库存和流水


第一版模拟支付的推荐规则
1. 支付模块先校验支付单和订单状态。
2. 支付最终确认与订单转换为 PAID、库存转换为 sold 在同一个 MySQL 事务内完成。
3. 超时关单与库存释放也必须在同一个 MySQL 事务内完成。
4. 支付与关单通过订单记录上的排他性处理和条件状态更新竞争。
5. 未取得合法状态转换权的操作不得修改库存。
6. 模拟支付成功不得发生在系统已经有效关闭订单之后。
需要特别区分真实支付渠道： 真实外部资金支付可能在本系统关单前已经成功，但回调延迟到达。那时不能简单忽略成功回调，而要查询渠道结果、关闭支付单或发起退款补偿。
FlashTicket V1 采用内部可控的模拟支付，所以可以建立清晰的原子确认点。后续设计模拟支付模块时，应把这个原子确认点作为强制约束。
八、订单信息与交易快照
订单创建后，不能每次都动态读取当前活动和票档配置来计算历史成交信息。
例如用户以 399 元购买一张票，运营第二天把同票档价格改成 499 元，这笔订单仍必须显示 399 元。
因此建议订单保存不可变交易快照。

建议记录：
- ORDER_CREATED
- PAYMENT_CONFIRMED
- USER_CANCELLED
- TIMEOUT_CLOSED
- SYSTEM_CLOSED

十五、订单模块 V1.0 最终决策
FlashTicket 订单与交易状态机方案


订单模型： 一笔订单对应一个场次、一个票档，可购买 1–2 张。
订单状态： PENDING_PAYMENT → PAID / CLOSED，退款使用独立状态机。
支付期限： 订单创建后 15 分钟。
创建方式： 仅允许由成功的抢票业务创建订单，不对用户端提供绕过抢票的普通下单入口。
库存协同： 创建订单、预占库存、限购占用在同一个 MySQL 本地事务中完成。
并发控制： 通过条件状态更新、行锁、唯一索引与事务解决重复创建、支付关单竞争和重复释放。
超时机制： RocketMQ Delay + Spring Scheduling 扫描兜底。
数据历史： 保存成交快照及订单状态操作记录。
异常恢复： Outbox、Inbox、幂等和数据库状态对账。
