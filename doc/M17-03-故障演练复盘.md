# FlashTicket 故障注入演练与复盘（M17-03）

> 生成时间：2026-10-16 · 演练环境：Docker 中间件 + 后端 local profile（模式3 Redis 准入）

## 1. 演练目标

验证四类故障下系统的可靠性与恢复能力：MQ 故障、Redis 故障、应用崩溃、MySQL 死锁。核心验证点：**故障期间不丢消息、不超卖、不重复建单，恢复后自动收敛到正确状态**。

## 2. 已实测演练

### 2.1 MQ 故障（RocketMQ broker/proxy 停）— ✅ 通过

| 步骤 | 现象 |
|------|------|
| `docker stop` broker + proxy | MQ 不可用 |
| 抢票 3 次（3 个不同用户） | 受理正常，返回 `SUCCESS QUEUED`（202） |
| 观察 Outbox | `ft_outbox_event` 累积 **PENDING=3**（消息可靠落地，未丢） |
| `docker start` broker + proxy | MQ 恢复 |
| 等待 ~20s（Outbox Publisher 扫描 1s + 补发） | PENDING → SENT，全部补发 |
| 观察请求/订单 | `ft_purchase_request` **SUCCEEDED=3**，`ft_order` **3 笔订单** |

**结论**：MQ 故障期间抢票受理不丢（Outbox 可靠落地），恢复后自动补发建单，**3 请求 → 3 订单，无丢失、无重复**（Inbox 幂等正确）。

### 2.2 Redis 重启 — ✅ 通过

| 步骤 | 现象 |
|------|------|
| `docker restart` redis | Redis 重启（有持久化 volume，RDB/AOF） |
| 观察 admission 快照 | 重启后快照仍在（持久化未丢） |
| 抢票 | `SUCCESS QUEUED`，不阻断 |

**结论**：Redis 有持久化，重启不丢 admission 快照，抢票不受影响。

### 2.3 Redis admission 快照丢失 — ✅ 通过（FALLBACK 验证）

| 步骤 | 现象 |
|------|------|
| `DEL ft:inventory:admission:{tierId}` | 仅删除库存准入快照 |
| 抢票 | `SUCCESS QUEUED`，**快照缺失自动 FALLBACK 到 MySQL 权威账本** |

**结论**：模式3 的 Redis 准入在快照缺失时自动回退 MySQL 预检，不阻断、不超卖；后续定时对账（10s）用 MySQL 权威重建快照。

### 2.4 Redis FLUSHALL（会话数据丢失）— ⚠️ 发现

| 步骤 | 现象 |
|------|------|
| `FLUSHALL` | 清空所有 Redis 数据 |
| 抢票 | `UNAUTHORIZED 未认证或凭据无效` |

**发现**：Redis 同时承载**会话/Refresh Token**（M02 max-sessions=5 的设备会话），FLUSHALL 会连带使已登录用户 token 失效，需重新登录。这是「Redis 是会话存储」的正确行为，但也提示：生产环境 Redis 故障会影响所有在线会话，需考虑会话重建策略（P1）。

## 3. 机制说明（已有集成测试覆盖，未单独实弹演练）

### 3.1 应用崩溃（后端进程 kill）

- **Outbox 持久化**：抢票受理与 Outbox 写入同事务（MySQL），应用崩溃不丢已受理请求。
- **执行租约恢复**：消费者领取租约（QUEUED→PROCESSING，`lease_until`）；应用崩溃后租约过期，恢复扫描三类兜底——租约过期→RECOVERING、RECOVERING 到点补发新 eventId、QUEUED 超时→FAILED(QUEUE_TIMEOUT)。
- 该机制已由 M12 集成测试覆盖（请求恢复扫描 + 幂等），本次 MQ 故障演练已实测验证了同源的 Outbox 补发路径。

### 3.2 MySQL 死锁

- 库存扣减用手写**条件更新**（`UPDATE ... SET available=available-? WHERE available>=? AND version=?`），判定受影响行数，**不用 @Version 插件、不用悲观锁**，从源头规避大部分死锁。
- 订单支付/关单互斥用对称条件更新（`paidById` / `closeById` 均 `WHERE status=...`），避免锁冲突。
- 若极端并发下仍触发死锁，依赖 Spring 事务重试 + BizException 返回用户可重试（P1 可加 @Retryable）。

## 4. 复盘结论

1. **可靠性机制经实测有效**：MQ 故障下 Outbox/Inbox 保证「受理不丢、恢复不重」，是本项目最关键的高可用能力。
2. **Redis 准入设计正确**：快照缺失自动 FALLBACK MySQL，不牺牲正确性（符合「先正确再优化」原则）。
3. **Redis 职责需关注**：Redis 同时承载库存准入 + 会话，生产需评估会话重建策略与 Redis 高可用（哨兵/集群）。
