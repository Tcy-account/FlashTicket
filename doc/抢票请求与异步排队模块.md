FlashTicket 业务需求设计 04：抢票请求与异步排队模块
推荐方案 V1.0
Purchase Request & Async Queue

这是 FlashTicket 的高并发请求入口，负责把用户瞬间涌入的抢票流量，转化为可控制、可追踪、可恢复的异步交易请求。
上一模块已经解决了库存如何安全预占、确认和释放。本模块重点解决：
- 10 万用户同时点击抢票，服务端如何接收和控制流量？
- 如何防止用户重复提交、超额购买和恶意刷票？
- 抢票请求如何可靠进入 RocketMQ？
- 用户看到“排队中”究竟代表什么？
- RocketMQ 消费失败、重复投递、积压后怎么办？
- 如何将结果实时通知 Vue 用户端？
本轮仍然只设计业务、架构、状态机、接口与验收条件，不写 Java 代码。
一、首先确定四个容易混淆的概念
概念	含义	是否代表买到票
请求已受理	MySQL 持久化抢票请求成功	否
进入排队	抢票事件已发布或等待可靠投递	否
库存预占成功	MySQL 已确认用户占用指定票量	尚未完成购买
支付成功	订单支付确认、库存转为已售	是
最重要的业务原则：排队成功 ≠ 抢票成功 ≠ 支付成功。
前端不允许仅凭 HTTP 200 或 QUEUED 提示“抢票成功”。只有订单创建且库存预占确认后，才显示“抢票成功，请完成支付”。

三、完整抢票业务流程
我推荐采用：
MySQL 可靠受理 → Outbox → RocketMQ → 库存预占 → 创建订单 → 结果通知。
这是第一版主链路。Redis Lua 库存高速预占在后续优化阶段加入。
1. 用户点击立即抢票
   选择票档和数量，提交稳定的 requestId。
2. 同步基础校验
   Spring Security 认证、请求合法性、活动销售资格、初步限购和限流。
3. 可靠受理
   MySQL 同一事务写入抢票请求和 Outbox 事件。
4. 立即返回受理结果
   返回 requestId 和 QUEUED，HTTP 使用 202 Accepted。
5. 异步消息发布
   Outbox Publisher 将事件发布到 RocketMQ ft-purchase。
6. 消费端处理
   根据请求 ID 去重，再次检查销售资格和最终限购状态，调用库存模块预占。
7. 创建订单
   在 MySQL 本地事务中协调库存预占、订单创建、请求状态更新和后续 Outbox 事件。
8. 通知结果
   成功返回订单编号和支付期限；售罄、限购等失败返回明确原因。

这里利用的是我们采用模块化单体、订单和库存共用一个 MySQL 数据库的优势：不必强行把预占和订单创建拆成两个分布式事务。
消费者侧库存预占、订单创建、抢票请求终态更新，可以放进同一个本地事务。
即使 RocketMQ 重复投递，也不会产生重复的有效订单。
四、抢票请求状态机
本模块建议维护自己的请求状态，不直接复用库存预占状态或订单状态。
QUEUED
请求已可靠受理，等待处理


PROCESSING
消费者取得处理资格


SUCCEEDED
订单已创建，库存已预占


FAILED
确定性业务失败



RECOVERING
处理结果暂时不确定，等待恢复

RECOVERING 是异常恢复状态，不是从成功或失败终态自动回退。正常已完成的请求保持不可逆终态。
状态规则
状态	解释	是否可重试
QUEUED	已受理但尚未完成处理	可以重新投递同一请求
PROCESSING	某个消费者正在处理	租约到期后允许恢复
RECOVERING	结果不确定或依赖异常	可恢复，不直接生成新请求
SUCCEEDED	订单创建成功	不重复执行
FAILED	明确失败，如售罄或限购	不自动转成功
CANCELLED	用户明确撤销尚未开始处理的请求	终态
重要补充：PROCESSING 不能永久卡住
建议采用 MySQL 处理租约：
- ownerToken：本次处理者标识。
- leaseUntil：处理租约截止时间。
- attemptCount：处理尝试次数。
- version：状态版本。
消费者要通过条件更新领取处理资格。租约超时后其他消费者才能重新领取，并通过新的处理令牌阻止旧处理者提交。
不能只在 Redis 设置一把锁，就认为已经避免所有重复消费。
五、抢票资格与限购规则
抢票资格需要分层校验。
5.1 入口校验
HTTP 同步校验负责尽早拒绝无效请求：
校验	规则
用户身份	必须登录，账号状态正常
活动状态	已发布、未取消
场次状态	正常
票档状态	启用
售票时间	当前处于有效销售窗口
购买数量	大于 0，不超过每单最大购买量
用户限流	没有超过 Redis 限流策略
请求重复	相同 requestId 返回已有状态
此时判断的余票是前置过滤，不保证最后能抢到。
5.2 消费端最终校验
消费者真正创建订单之前，必须重新验证相关业务条件。
尤其是：
- 活动是否刚刚暂停。
- 票档是否刚刚停止销售。
- 用户是否被禁用。
- 用户是否已经达到购买上限。
- 当前是否有足够可售库存。
这样可以避免请求排队期间业务状态变化造成错误售票。
5.3 用户限购如何统计？
假设票档规定每用户最多买 2 张。
不能简单统计历史已支付票数，因为用户可能同时提交多个请求，每个都尚未支付。
限购占用量建议定义为：
\[
已支付有效票数+未支付有效预占票数
\]

其中已取消、已释放的订单不再占用限购名额。
但要处理并发：两个各买 2 张的请求可能同时检查到用户还没买票，因此消费端需要在同一事务中以用户和票档为维度进行原子限购占用或串行化控制。
Redis 只能辅助快速拒绝，最终不能依赖先查数量再下单的非原子逻辑。

七、流量削峰、排队容量与过载控制
RocketMQ 能够缓冲消息，但消息队列不是无限容量的请求蓄水池。
必须设计入口过载保护。
推荐的四层控制
层级	保护对象	推荐策略
第一层	HTTP 请求入口	用户、IP、活动维度 Redis 限流
第二层	抢票受理写入	限制每秒受理量与待处理请求数量
第三层	RocketMQ 消费端	有界并发和按下游能力限速
第四层	MySQL / 库存	条件更新、连接池、库存预算
例如，当订单消费端只能稳定处理每秒 500 个请求，而入口持续接收每秒 5,000 个请求，积压会持续增长。
因此必须监测队列积压、最早待处理请求等待时间、订单处理速率，达到阈值时应降级或拒绝新请求。
初始业务参数建议
参数	初始规划
每单购买数量	1–2 张
同一用户每票档限购	2 张
同用户同票档有效待处理请求	最多 1 个
单账号抢票请求限流	初始每 5 秒 1 次新请求
排队最大等待时长	60 秒（实验参数）
订单支付有效期	15 分钟
超负载行为	返回明确的繁忙 / 稍后重试
请求幂等记录	至少覆盖购票、关单及重试生命周期
这里的每秒处理量和 60 秒排队上限都应经过压测调整，不是固定行业标准。
达到等待上限时，也不能把还在执行或结果未知的请求直接标记成失败。必须先阻止它继续执行、确认没有创建订单或预占库存，再进入最终失败状态。

8.2 Outbox 保障什么？
用户提交抢票请求时，在同一个 MySQL 事务中完成：
1. 创建 ft_purchase_request。
2. 创建对应的 ft_outbox_event。
3. 提交事务。
4. 返回 202 Accepted。
这意味着应用即使在 HTTP 返回之后崩溃，请求及待发送事件仍然保留。
Outbox 后台任务重试发送消息直到 Broker 确认或进入待人工干预状态。
Outbox 保证的是请求与待发布事件同时持久化，不是保证抢票必然成功。
8.3 消费端事务
消费者收到消息后：
- 校验事件 ID 与请求状态。
- 获取当前处理资格。
- 重新验证业务规则。
- 调用库存服务。
- 创建待支付订单。
- 更新抢票请求状态。
- 写入需要发布的后续事件。
关键 MySQL 写入使用本地事务。
消息可能在本地事务提交后、消费者返回成功前重新投递，因此消费端必须能通过请求终态和订单唯一索引识别已完成处理。
8.4 暂时失败与最终失败
场景	处理方式
库存确定不足	FAILED，原因 SOLD_OUT
已达限购数量	FAILED，原因 LIMIT_EXCEEDED
售票暂停	根据准入规则，标记不可继续处理
MySQL 临时不可用	保持可恢复状态并重试
RocketMQ 暂时不可用	Outbox 等待重发
消费者崩溃	处理租约到期后恢复
数据库提交结果未知	查询请求与订单记录，再判定结果
消息重复	幂等返回，不能重复扣库存
消费者重试需要区分可重试系统错误和不可重试业务错误。否则售罄请求可能一直进入消息重试，占用不必要的资源。
九、Redis 在抢票模块的职责
我们已经为 Redis 库存模块设计了 Lua 高速预占，这里再增加抢票入口管理。
Key	数据类型	作用
ft:purchase:rate:user:{userId}	String	用户请求限流
ft:purchase:rate:event:{eventId}	String	活动级限流
ft:purchase:rate:ip:{ipHash}	String	IP 防刷

需要注意：
- MySQL 请求记录才是请求状态的权威来源。
- Redis 排队数量是辅助指标，不直接用作最终准确排名。
- 缓存状态更新失败不能改变已经提交的订单结果。
- Redis 状态 Key 应有合适 TTL，但不能过期后重新接受同一个旧请求并创建第二笔订单。
- 排队计数丢失后，应通过 MySQL 请求状态和 MQ 指标重新统计或修复。
不建议单独使用 Redis List 再维护另一套抢票队列，否则会和 RocketMQ 重复承担任务调度职责，增加跨队列一致性问题。
十、SSE 实时状态通知
前端已经确定使用 Vue 3 + Axios，实时结果采用：
SSE 推送 + HTTP 状态查询兜底。
Spring MVC 可以通过 SseEmitter 实现服务端事件推送，适合服务器向浏览器单向发送状态更新的场景。
推荐的事件类型
事件	说明
purchase.queued	请求已可靠受理
purchase.processing	开始处理
purchase.succeeded	订单创建成功
purchase.failed	确定性业务失败
purchase.recovering	状态暂时不确定
purchase.cancelled	请求取消
heartbeat	心跳保活
前端状态流转的原则：
- 页面刷新后使用 requestId 恢复查询。
- SSE 断开不代表抢票失败。
- SSE 事件携带请求状态版本，避免乱序事件覆盖更新状态。
- 事件丢失后通过 GET 请求获取最新权威状态。
- 不保证推送事件恰好送达一次。
- 用户只能订阅属于自己的抢票请求。
- SSE 鉴权使用现有会话方案，不在 URL 中携带长期凭证。
单体系统如何实现推送？
第一版可以采用：
- 订单处理完成后，通知当前应用实例中的 SSE 订阅者。
- SSE 建立连接时先读取当前请求状态。
- 前端定期兜底查询。
- 断线后重新连接并同步最新状态。
如果以后部署多个 Spring Boot 实例，消费者可能运行在 A 实例，用户 SSE 连接却在 B 实例。届时需要 Redis Pub/Sub 或其他跨实例通知机制。
Redis Pub/Sub 只用于实时提示，不承担可靠业务事件存储。可靠结果仍在 MySQL。
另外，Spring MVC SSE 长连接需要合理设置连接超时、最大连接数和线程资源；不能不加限制地允许每个用户无限创建 SSE 连接。
十一、数据库实体规划
此时不展开 DDL，先确定业务实体和关键约束。
实体	主要职责	关键约束
ft_purchase_request	持久化抢票请求及终态	request_id 唯一
ft_purchase_attempt	记录消费处理尝试和失败原因	关联请求、处理租约
ft_purchase_limit	用户与票档的限购占用账目	(user_id, tier_id) 唯一
ft_outbox_event	可靠发布抢票事件	event_id 唯一

ft_reservation	库存预占	request_id 唯一
ft_order	最终订单	request_id 唯一
其中 ft_purchase_attempt 可以放在 P1，实现基础异常重试时先在抢票请求中保留尝试次数、错误码、租约与恢复信息。
限购占用应随订单确认、取消和库存释放在一致的事务规则下变化，不能通过非原子的普通 SELECT COUNT 保证并发正确性。
请求编号设计
建议区分三个 ID：
- requestId：一次用户抢票操作的全局幂等标识。
- eventId：一次 MQ 业务事件的标识。
- orderId：订单实体主键。
三者不能混用。一个请求可以经历多次消息投递和处理尝试，但最多产生一个有效订单。

十五、模块 V1.0 最终决策
FlashTicket 抢票请求与异步排队模块定稿


排队模型： 异步处理队列，不承诺严格 FIFO 或精确排名。
可靠受理： MySQL 抢票请求 + Outbox 同事务提交，返回 HTTP 202。
消息处理： RocketMQ Normal 消息、PushConsumer 集群消费。
幂等与并发： requestId 唯一约束、请求状态机、处理租约、消费幂等、数据库条件更新。
限购与限流： Redis 多维限流 + MySQL 最终限购原子占用。
库存与订单： 模块化单体内优先采用 MySQL 本地事务协调预占、订单和请求状态。
实时结果： SSE + HTTP 查询兜底，MySQL 结果为最终依据。
异常恢复： Outbox 补发、MQ 重试、租约恢复、死信处理、对账扫描。
优化路线： MySQL 正确性基线 → RocketMQ 异步削峰 → Redis Lua 高速预占。
