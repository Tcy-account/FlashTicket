FlashTicket 业务需求设计 02：演出活动与场次模块
推荐方案 V1.0
Event & Session Management · 业务需求设计

本模块负责平台从创建演出、配置场次、设置票档和售票时间，到审核发布、开始售票、暂停销售、演出结束的完整运营生命周期。
它将直接决定后续库存中心、抢票中心、订单中心如何设计。
本次先确定业务规则、状态机、功能边界、数据实体、接口清单和验收标准，不编写代码或数据库 DDL。

概念	定义	示例
Event 演出活动	用户浏览的演出项目	某歌手巡回演唱会
Session 场次	某一具体时间和地点的演出	5 月 1 日晚场

三者关系为：
- 一个演出活动可包含多个场次。
- 一个场次可包含多个票档。
- 每个票档拥有独立库存。
- 一个票档第一版对应一个正式售票时间窗口。
- 第一版不支持选座，后续增加固定座位票。
这个设计符合票务系统中不指定座位票（General Admission）与指定座位票的常见区别：前者主要管理数量，后者还需要管理具体座位的可用性。

3.3 活动生命周期
演出活动状态机
DRAFT 草稿


PENDING_REVIEW 待审核


REJECTED
审核拒绝，可修改后重新提交


PUBLISHED

审核拒绝可返回草稿修改；已发布活动不允许直接退回草稿。归档和取消仅能通过符合业务规则的操作触发。
非常重要：活动发布状态不等于售票状态。
例如活动已经发布，但仍然可以显示“尚未开售”。也可能活动正常发布，而其中一个场次已经售罄。
因此不能把活动状态简单设计成 未开始 / 抢票中 / 售罄 / 已结束。
这些是不同维度的状态，需要分别管理。
3.4 审核和发布规则
建议由 OPERATOR 创建和提交活动，由具备 event:review 权限的 SUPER_ADMIN 执行审核。
第一版规则：
- 创建草稿时只需填写必要字段。
- 提交审核时，必须完成活动、至少一个有效场次、票档和售票时间配置。
- 审核人不能审核自己提交的活动。
- 审核拒绝必须填写原因。
- 审核通过后生成发布版本，用户端只展示已发布版本。
- 关键内容变更需要重新审核。
- 发布及审核操作记录审计日志。
这样可以避免“管理员随意更改正在售卖的演出内容”造成订单与展示信息不一致。
四、场馆管理 Venue
场馆是场次的承载地点，一个场馆可以用于多个不同活动。
4.1 场馆基础信息
字段	说明
场馆 ID	雪花 ID
场馆名称	例如：星光体育馆
国家 / 省 / 城市 / 区县	用于搜索及筛选
详细地址	线下观演地点
时区	IANA 时区，如 Asia/Shanghai
最大核定容量	场馆可容纳人数上限
场馆介绍	简介、入场说明
状态	启用 / 停用
创建 / 更新信息	操作审计
容量规则： 同一场次所有票档的票量总和不能超过该场次配置的可售容量，而场次可售容量不能超过场馆核定容量。
需要区分场馆最大容量和特定场次实际开放容量。例如场馆可以容纳 10,000 人，但某场演出只开放 6,000 人。
P1 可以扩展多个演出厅、不同座位区域和完整座位图。
五、场次管理 Session
一个演出活动可以有多个场次，同一个场次只属于一个演出。
5.1 场次信息
字段	规则
场次 ID	雪花 ID
所属活动	必填
场次名称	例如：周六晚场
场馆	必填
演出开始时间	必填
预计结束时间	必填，晚于开始时间
检票开始时间	可选
可售容量	必填
场次状态	由状态机控制
取消 / 延期原因	对应操作时必填
创建 / 更新时间	自动记录
5.2 场次状态
状态	含义	允许售票
SCHEDULED	正常安排	取决于销售计划
POSTPONED	已延期	否
CANCELLED	已取消	否
COMPLETED	演出完成	否
不建议给场次设置一个冗余的 SELLING 状态。是否可以购买应由场次有效性、销售窗口、票档状态和库存共同判断。
5.3 场次时间冲突规则
同一场馆若不支持同时举行多个活动，同一时间段不能分配给两个场次。
例如：
场次	开始	结束	是否冲突
A	19:00	21:00	—
B	20:00	22:00	与 A 冲突
C	22:30	23:30	不冲突
第一版建议把场馆视为单一可排期资源，并设置可配置的清场缓冲时间，默认 30 分钟。
后续如果需要支持同一场馆多个独立演出厅，再引入 VenueHall，由演出厅负责时间占用约束。
并发创建或修改场次时，冲突检查也必须具备数据库级互斥或其他可靠串行化保护，不能只先查询再插入。
5.4 延期和取消规则
没有有效交易的场次： 可以由运营人员修改时间、场馆、容量等，但已发布活动的关键变更仍应审核。
已经有有效订单的场次： 不允许直接静默修改演出时间或场馆。应进入延期流程，记录变更原因，并通知受影响用户。
取消场次： 立即禁止新抢票，原有订单通过取消及模拟退款流程处理，不得直接删除订单。
完成演出： 不得再抢票、恢复销售或新增正常购买订单。

6.2 票档业务规则
- 同一场次可以创建多个票档。
- 票档名称只需在同一场次内唯一。
- 票价在有效订单产生后不得直接覆盖历史成交价格。
- 订单必须保存购买时的票档名称、票价及关键售票规则快照。
- 库存扣减及释放由库存中心统一负责，活动模块不得直接修改库存计数。
- 销售中需要增减票量时，必须走独立的库存调整流程，且需要审计；不能直接覆盖初始库存字段。
- 有效已售数量和有效预占数量不能因调整而失去对应的库存账目。
- 不允许删除已有抢票或订单引用的票档。
票档编辑和库存调整是两个不同业务操作，后续 API 也应分开。

7.2 销售状态应该怎么计算？
建议采用三个层次：
第一层：运营手动控制状态
- ENABLED：允许按计划销售。
- PAUSED：运营人员暂停销售。
第二层：时间窗口
- NOT_STARTED：未到开售时间。
- IN_PROGRESS：处于售票时间窗口。
- ENDED：已超过售票结束时间。
第三层：库存展示
- AVAILABLE：有可售库存。
- SOLD_OUT：当前无可用库存。
最终前端展示状态由三者共同计算。

八、后台运营业务流程
整体流程建议设计为：
1. 创建演出活动
   填写演出名称、类型、封面、详情及主办方。
2. 选择或创建场馆
   确定城市、地址、时区及场馆容量。
3. 创建演出场次
   配置演出时间、场馆和场次可售容量。
4. 配置票档与库存
   设置 VIP、普通等票档，配置价格、初始库存及限购。
5. 设置售票计划
   配置每个票档的公开售票开始和结束时间。
6. 提交审核并发布
   检查活动内容、容量约束、时间有效性，审核通过后生成发布快照。
7. 等待开售并预热
   开售前检查配置、初始化 Redis 销售入口状态，并完成库存核对。
8. 正式售票
   用户通过抢票中心请求购票。运营后台可监测、暂停或恢复销售。
9. 结束售票和演出
   销售截止后不再接收新抢票；场次完成后进入历史管理。

十、关键异常场景与处理原则
这部分是 FlashTicket 与普通 CRUD 项目拉开差距的地方。
异常场景	业务处理原则
两个运营人员同时编辑同一活动	使用版本号防止覆盖更新
两人同时提交审核和修改票档	固定审核版本，拒绝过期修改
同一场馆被并发创建两个冲突场次	场馆排期串行化校验，禁止冲突
活动已发布，但票档库存初始化失败	不开放抢票，进入待修复状态
到达开售时间，但定时任务未执行	服务端根据权威时间判断资格，不只依赖调度器
开售瞬间暂停销售	定义在途请求边界，停止新请求，已确认预占继续按交易规则处理
暂停后有订单超时释放库存	允许内部释放，但不允许新的预占
演出取消时仍有未支付或已支付订单	阻止新交易，启动订单关闭与退款流程
库存为零，但订单超时退票	可重新出现余票，前提是售票窗口仍有效
运营人员修改已成交票档价格	不影响历史订单快照
活动发布时缓存更新失败	数据库发布成功后可靠失效或重建缓存，避免旧缓存长期生效
特别建议给售票计划引入销售配置版本号。开售、暂停、恢复、销售时间变更和正式售票配置发布都需要维护版本。后续抢票系统可以据此识别过期配置，避免使用旧缓存错误放行请求。

本模块最终确定的规则
FlashTicket · 演出活动与场次模块 V1.0

业务关系： Event → Session → Ticket Tier，每个票档绑定独立 Sale Plan。
售票类型： 首期数量型票，不指定具体座位。
发布流程： 运营创建 → 提交审核 → 超级管理员审核 → 发布展示。
场次管理： 支持多个场次、场馆容量约束、时间冲突校验、延期与取消。
销售控制： 独立的开售窗口、手动暂停、恢复销售和库存售罄状态。
高并发边界： 活动模块判断售票资格，库存模块保证不会超卖，抢票模块负责排队和请求幂等。
历史一致性： 活动配置与已成交订单通过版本和业务快照隔离。
